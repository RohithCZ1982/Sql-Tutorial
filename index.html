SQL Server and T-SQL Fundamentals

The foundation every later module depends on
8 hours Lecture + Lab

Learning objectives

  • Describe how an instance, a database, a schema and the system databases fit together, and where a query's memory and temporary work actually happen.
  • Write multi-table queries confidently using every join type, GROUP BY/HAVING, subqueries and common table expressions.
  • Solve ranking, running-total and row-comparison problems with window functions instead of cursors or self-joins.
  • Predict how NULL, data-type precedence and implicit conversion change a result set — and a query plan.
  • Explain what a transaction guarantees, and how each isolation level trades blocking against consistency.

Key concepts

The instance / database / schema hierarchy

A SQL Server instance is one running copy of the engine: it owns the memory, the worker threads, tempdb, logins and server-level configuration. Inside it sit databases, each with its own data files, transaction log and users. Inside a database, a schema (dbo, sales, staging) is a namespace and a permission boundary. Always write four-part-aware names in code — use dbo.Orders, never bare Orders. It saves a plan-cache lookup and it removes ambiguity when two schemas have the same table name.

Logical processing order — why WHERE cannot see an alias

T-SQL is written in one order and evaluated in another. Teach this order early; it explains half of the errors beginners hit:

Logical query processing order
FROM  →  ON  →  JOIN  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  DISTINCT  →  ORDER BY  →  TOP/OFFSET
                              ▲                     ▲            ▲                         ▲
                    row filter, no aliases   group filter   aliases created here   aliases usable here

That is why WHERE TotalWithTax > 100 fails when TotalWithTax is a SELECT alias, but ORDER BY TotalWithTax works. Wrap the expression in a CTE or a derived table when you need to filter on it.

Joins: the four you need and the one to avoid

  • INNER JOIN — rows that match on both sides. The default choice.
  • LEFT JOIN — every left row, NULL-padded when there is no match. Use it for "customers with or without orders".
  • FULL JOIN — both unmatched sides. Rare outside reconciliation work (very useful in Module 9 for POS vs. D365 comparisons).
  • CROSS JOIN — deliberate Cartesian product, e.g. building a date × store grid.
  • CROSS/OUTER APPLY — a join to a correlated table expression; the right way to do "top 3 per group".
Example · join types side by side
-- 1. INNER: customers who actually ordered
SELECT c.CustomerID, c.CustomerName, COUNT(o.OrderID) AS OrderCount
FROM dbo.Customer AS c
INNER JOIN dbo.Orders AS o ON o.CustomerID = c.CustomerID
GROUP BY c.CustomerID, c.CustomerName;

-- 2. LEFT: include customers with zero orders (note COUNT(o.OrderID), not COUNT(*))
SELECT c.CustomerID, c.CustomerName, COUNT(o.OrderID) AS OrderCount
FROM dbo.Customer AS c
LEFT JOIN dbo.Orders AS o ON o.CustomerID = c.CustomerID
GROUP BY c.CustomerID, c.CustomerName
ORDER BY OrderCount ASC;

-- 3. Anti-join: customers who never ordered
SELECT c.CustomerID, c.CustomerName
FROM dbo.Customer AS c
WHERE NOT EXISTS (SELECT 1 FROM dbo.Orders AS o WHERE o.CustomerID = c.CustomerID);

-- 4. CROSS APPLY: three most recent orders per customer
SELECT c.CustomerName, x.OrderID, x.OrderDate, x.TotalAmount
FROM dbo.Customer AS c
CROSS APPLY (
    SELECT TOP (3) o.OrderID, o.OrderDate, o.TotalAmount
    FROM dbo.Orders AS o
    WHERE o.CustomerID = c.CustomerID
    ORDER BY o.OrderDate DESC
) AS x;

Watch this one

Putting a condition on the right table of a LEFT JOIN in the WHERE clause silently converts it into an inner join, because NULL fails every comparison. If the filter belongs to the outer table, it goes in the ON clause: LEFT JOIN dbo.Orders o ON o.CustomerID = c.CustomerID AND o.Status = 'Closed'.

GROUP BY, HAVING and aggregate rules

Every non-aggregated column in the SELECT must appear in GROUP BY. WHERE filters rows before grouping; HAVING filters groups after. Filter as early as possible — a predicate in WHERE reduces the rows the aggregate has to chew through, whereas the same predicate in HAVING does not.

Example · aggregation with the filter in the right place
-- Stores whose 2026 revenue exceeded 5,000,000, counting only closed orders
SELECT  o.StoreID,
        COUNT(*)            AS ClosedOrders,
        SUM(o.TotalAmount)  AS Revenue,
        AVG(o.TotalAmount)  AS AvgTicket,
        MAX(o.OrderDate)    AS LastOrderUtc
FROM    dbo.Orders AS o
WHERE   o.Status = 'Closed'                        -- row filter: cheap, runs first
  AND   o.OrderDate >= '2026-01-01'
  AND   o.OrderDate <  '2027-01-01'
GROUP BY o.StoreID
HAVING  SUM(o.TotalAmount) > 5000000               -- group filter: only aggregates belong here
ORDER BY Revenue DESC;

Subqueries and common table expressions

A CTE is a named result set that lives for one statement. It does not materialise anything by itself — it is readability, not a performance feature. Its real power is recursion and the ability to stack transformations in the order a human thinks about them.

Example · layered CTEs and a recursive CTE
-- A. Layered CTEs: monthly revenue, then month-over-month growth
WITH MonthlySales AS
(
    SELECT  DATEFROMPARTS(YEAR(o.OrderDate), MONTH(o.OrderDate), 1) AS SalesMonth,
            SUM(o.TotalAmount) AS Revenue
    FROM    dbo.Orders AS o
    GROUP BY DATEFROMPARTS(YEAR(o.OrderDate), MONTH(o.OrderDate), 1)
),
WithPrior AS
(
    SELECT  SalesMonth,
            Revenue,
            LAG(Revenue) OVER (ORDER BY SalesMonth) AS PriorRevenue
    FROM    MonthlySales
)
SELECT  SalesMonth,
        Revenue,
        PriorRevenue,
        CASE WHEN PriorRevenue IS NULL OR PriorRevenue = 0 THEN NULL
             ELSE CAST(100.0 * (Revenue - PriorRevenue) / PriorRevenue AS DECIMAL(6,2))
        END AS GrowthPct
FROM    WithPrior
ORDER BY SalesMonth;

-- B. Recursive CTE: employee reporting hierarchy with depth
WITH OrgChart AS
(
    SELECT EmployeeID, EmployeeName, ManagerID, 0 AS Level,
           CAST(EmployeeName AS NVARCHAR(1000)) AS Path
    FROM   dbo.Employee
    WHERE  ManagerID IS NULL                        -- anchor member

    UNION ALL

    SELECT e.EmployeeID, e.EmployeeName, e.ManagerID, oc.Level + 1,
           CAST(oc.Path + N' > ' + e.EmployeeName AS NVARCHAR(1000))
    FROM   dbo.Employee AS e
    JOIN   OrgChart     AS oc ON e.ManagerID = oc.EmployeeID   -- recursive member
)
SELECT EmployeeID, EmployeeName, Level, Path
FROM   OrgChart
ORDER BY Path
OPTION (MAXRECURSION 50);                            -- always cap recursion

Window functions

A window function computes across a set of rows related to the current row without collapsing them. OVER() takes three parts: PARTITION BY (reset the calculation per group), ORDER BY (define sequence) and an optional frame (ROWS BETWEEN ...). If you find yourself writing a self-join to compare a row with its neighbour, you want a window function.

FunctionBehaviour on tiesTypical use
ROW_NUMBER()Always unique, ties broken arbitrarilyDe-duplication, paging
RANK()Ties share a rank, then gaps (1,1,3)Competition-style ranking
DENSE_RANK()Ties share a rank, no gaps (1,1,2)"Top 3 distinct salaries"
NTILE(n)Splits into n bucketsQuartiles, deciles
LAG() / LEAD()Previous / next row valueDeltas, gap detection
SUM() OVERRunning or windowed totalCumulative revenue, moving average
Example · ranking, running totals and de-duplication
-- A. Salary rank inside each department (the syllabus sample, extended)
SELECT  EmployeeID,
        DepartmentID,
        Salary,
        RANK()       OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS SalaryRank,
        DENSE_RANK() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS DenseRank,
        ROW_NUMBER() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS RowNum,
        Salary - AVG(Salary) OVER (PARTITION BY DepartmentID)              AS DiffFromDeptAvg
FROM    dbo.Employee
ORDER BY DepartmentID, SalaryRank;

-- B. Running total and 7-day moving average of daily revenue
WITH Daily AS
(
    SELECT CAST(OrderDate AS DATE) AS SalesDate, SUM(TotalAmount) AS Revenue
    FROM   dbo.Orders
    GROUP BY CAST(OrderDate AS DATE)
)
SELECT  SalesDate,
        Revenue,
        SUM(Revenue) OVER (ORDER BY SalesDate
                           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal,
        AVG(Revenue) OVER (ORDER BY SalesDate
                           ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS MovingAvg7Day
FROM    Daily
ORDER BY SalesDate;

-- C. Delete duplicate customers, keeping the lowest CustomerID
WITH Dupes AS
(
    SELECT CustomerID,
           ROW_NUMBER() OVER (PARTITION BY Email ORDER BY CustomerID) AS rn
    FROM   dbo.Customer
    WHERE  Email IS NOT NULL
)
DELETE FROM Dupes WHERE rn > 1;   -- deleting through a CTE affects the base table

Frame default trap. When you supply ORDER BY without a frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which groups all tied values together and is slower than ROWS. For running totals, always write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW explicitly.

Data types, NULL and conversion

Pick the smallest type that fits the domain: DATE for a date, DATETIME2(3) for a timestamp, DECIMAL for money, NVARCHAR only when you genuinely need Unicode. Width matters — every byte in a clustered key is repeated in every nonclustered index (Module 5).

NULL means "unknown", so NULL = NULL is not true; use IS NULL. Aggregates ignore NULL (except COUNT(*)), and NOT IN against a list containing NULL returns no rows at all — a classic silent bug.

Example · NULL handling and conversion
-- NOT IN with NULL returns an empty set. NOT EXISTS does not.
SELECT COUNT(*) FROM dbo.Customer
WHERE CustomerID NOT IN (SELECT CustomerID FROM dbo.Orders WHERE CustomerID IS NOT NULL);

-- Safe form
SELECT COUNT(*) FROM dbo.Customer AS c
WHERE NOT EXISTS (SELECT 1 FROM dbo.Orders AS o WHERE o.CustomerID = c.CustomerID);

-- COALESCE vs ISNULL: COALESCE is ANSI, takes n arguments, and uses the
-- highest data-type precedence; ISNULL truncates to the FIRST argument's type.
SELECT ISNULL(CAST('ab' AS VARCHAR(2)), 'abcdef')  AS IsNullResult,   -- 'ab'
       COALESCE(CAST('ab' AS VARCHAR(2)), 'abcdef') AS CoalesceResult; -- 'ab' (both NOT NULL here)

-- Explicit conversion with failure tolerance (SQL Server 2012+)
SELECT TRY_CONVERT(DECIMAL(10,2), '123.45')  AS Ok,     -- 123.45
       TRY_CONVERT(DECIMAL(10,2), 'not-a-number') AS Bad; -- NULL, no error

-- Integer division trap
SELECT 7 / 2               AS IntDivision,        -- 3
       7 / 2.0             AS DecimalDivision,    -- 3.500000
       CAST(7 AS DECIMAL(9,2)) / 2 AS Explicit;   -- 3.50

-- Deterministic date literals: always use the unseparated ISO form
SELECT CAST('20260131' AS DATE) AS SafeLiteral;   -- never '31/01/2026'

Transactions and isolation levels

A transaction is an all-or-nothing unit of work. In SQL Server every statement is already a transaction; BEGIN TRAN groups several into one. The critical habit is to set XACT_ABORT ON and pair every BEGIN with error handling, otherwise a failure mid-batch can leave a transaction open and hold locks indefinitely.

Example · a correct explicit transaction
SET XACT_ABORT ON;      -- any error rolls the whole transaction back
SET NOCOUNT  ON;

BEGIN TRY
    BEGIN TRANSACTION;

    INSERT INTO dbo.Orders (CustomerID, StoreID, OrderDate, TotalAmount, Status)
    VALUES (17, 3, SYSUTCDATETIME(), 2450.00, 'New');

    DECLARE @NewOrderID INT = SCOPE_IDENTITY();   -- SCOPE_IDENTITY, never @@IDENTITY

    INSERT INTO dbo.OrderLine (OrderID, ProductID, Quantity, LineAmount)
    VALUES (@NewOrderID, 42, 2, 1200.00),
           (@NewOrderID, 77, 1, 1250.00);

    COMMIT TRANSACTION;
    SELECT @NewOrderID AS CreatedOrderID;
END TRY
BEGIN CATCH
    IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;   -- -1 = doomed, 1 = committable
    THROW;                                        -- re-raise with original number and line
END CATCH;

-- Session A
BEGIN TRANSACTION;
UPDATE dbo.Orders SET TotalAmount = TotalAmount + 1 WHERE OrderID = 100;

        DB_NAME(r.database_id) AS DbName, t.text AS RunningSql
FROM    sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE   r.blocking_session_id <> 0;

ROLLBACK TRANSACTION;

Common mistakes and pitfalls

  • SELECT * in application code. It breaks when a column is added, kills covering-index plans, and ships columns nobody uses. Name your columns.
  • WITH (NOLOCK) sprinkled everywhere. It is not a performance switch; it permits dirty and even duplicated rows. If readers block writers, turn on RCSI instead.
  • Filtering the outer table of a LEFT JOIN in WHERE, which quietly turns it into an INNER JOIN.
  • NOT IN with a nullable subquery column — returns zero rows. Use NOT EXISTS.
  • Ambiguous date literals like '01/02/2026'. Use '20260201' or DATEFROMPARTS.
  • Leaving a transaction open after an error because there was no TRY/CATCH and no XACT_ABORT.
  • Row-by-row loops and cursors for work a single set-based statement can do. Start set-based; reach for a cursor only when you have proven you need it.
  • @@IDENTITY instead of SCOPE_IDENTITY() — a trigger elsewhere will hand you the wrong key.

Practical exercises

  1. Join and aggregate drill (45 min) Produce one result set with: every city, the number of customers in it, the number of those customers who have never placed an order, total revenue, and average ticket size. Cities with no customers must still appear if you add a reference city list. Verify your zero-order count two ways — LEFT JOIN ... IS NULL and NOT EXISTS — and confirm they agree.
  2. Window function challenge (45 min) For each store, return the three highest-value orders, their rank, the running total of revenue by day, and the number of days since that store's previous order (LAG + DATEDIFF). Then rewrite the "top three" part without window functions using CROSS APPLY and compare which reads better.
  3. NULL and conversion hunt (30 min) Given the seeded Customer.Email column, write a query that finds rows where a naive NOT IN filter and a NOT EXISTS filter disagree. Explain the difference to the room in one sentence.
  4. Isolation lab, in pairs (40 min) One learner runs an uncommitted UPDATE; the other tries to read the row under READ COMMITTED, then READ UNCOMMITTED, then with RCSI enabled. Record what each returns and how long it waits. Finish by producing a deadlock deliberately (two sessions updating two rows in opposite order) and reading the deadlock graph in Extended Events.

Key takeaways

  • Logical processing order explains most beginner errors — aliases exist only from SELECT onward.
  • Filter in WHERE for rows, HAVING for groups, and ON when preserving an outer join.
  • Window functions replace self-joins and cursors for ranking, deltas and running totals; always state the frame.
  • NULL is "unknown", not "empty" — it changes comparisons, NOT IN and aggregates.
  • Every explicit transaction needs SET XACT_ABORT ON, TRY/CATCH and an XACT_STATE() check.
  • RCSI, not NOLOCK, is the correct answer to "readers are blocking writers".

Stored Procedures, Views, Functions, and Triggers

Putting logic in the database — and knowing when not to
8 hours Lecture + Lab

Learning objectives

  • Build a parameterised stored procedure with proper TRY/CATCH error handling, return values and output parameters.
  • Create views for reporting and controlled access, and explain what SCHEMABINDING and indexed views buy you.
  • Choose correctly between a scalar function, an inline table-valued function and a multi-statement function — and quantify the cost of the wrong choice.
  • Write AFTER and INSTEAD OF triggers that are set-based, and recognise when a trigger is the wrong tool.
  • Apply deployment and version-control practices so database objects ship like application code.

Key concepts

Why put logic in the database at all?

Three reasons that still hold: a stored procedure is a security boundary (grant EXECUTE on the procedure, not SELECT on the tables), it is a contract the application cannot bypass, and it keeps data-intensive work next to the data instead of dragging a million rows across the network. The counter-argument is testability and version control — which is why the last section of this module matters.

Stored procedures done properly

A production-grade procedure has: SET NOCOUNT ON (stops "n rows affected" chatter that confuses some clients), explicit parameter types and defaults, validation before work, a transaction when more than one statement must succeed together, and a CATCH block that rolls back and re-raises rather than swallowing the error.

Example · the syllabus procedure, production-hardened
CREATE OR ALTER PROCEDURE dbo.usp_GetOrdersByCustomer
    @CustomerID INT,
    @FromDate   DATE = NULL,
    @ToDate     DATE = NULL,
    @RowCount   INT  = NULL OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        /* --- validate inputs early and fail with a clear message --- */
        IF @CustomerID IS NULL OR @CustomerID <= 0
            THROW 50001, 'CustomerID must be a positive integer.', 1;

        IF NOT EXISTS (SELECT 1 FROM dbo.Customer WHERE CustomerID = @CustomerID)
            THROW 50002, 'Customer not found.', 1;

        SET @FromDate = ISNULL(@FromDate, '19000101');
        SET @ToDate   = ISNULL(@ToDate,   '99991231');

        /* --- named columns, not SELECT * --- */
        SELECT  o.OrderID,
                o.OrderDate,
                o.StoreID,
                o.TotalAmount,
                o.Status
        FROM    dbo.Orders AS o
        WHERE   o.CustomerID = @CustomerID
          AND   o.OrderDate  >= @FromDate
          AND   o.OrderDate  <  DATEADD(DAY, 1, @ToDate)
        ORDER BY o.OrderDate DESC;

        SET @RowCount = @@ROWCOUNT;
        RETURN 0;                       -- 0 = success, by convention
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;

        /* Log first, then re-raise so the caller still sees the failure. */
        INSERT INTO dbo.ErrorLog (ProcName, ErrorNumber, ErrorMessage, ErrorLine, LoggedUtc)
        VALUES (OBJECT_NAME(@@PROCID), ERROR_NUMBER(), ERROR_MESSAGE(), ERROR_LINE(), SYSUTCDATETIME());

        THROW;
        RETURN -1;
    END CATCH
END;
GO

THROW vs RAISERROR. Use THROW: it preserves the original error number, severity and line, and needs no pre-registered message. Use RAISERROR only when you need WITH NOWAIT for progress messages or printf-style formatting. Note the semicolon terminating the statement before THROW — it is required.

Writing procedures that modify data

Example · transactional insert with an OUTPUT clause and a MERGE-free upsert
CREATE OR ALTER PROCEDURE dbo.usp_CreateOrder
    @CustomerID INT,
    @StoreID    INT,
    @Lines      dbo.OrderLineType READONLY,   -- table-valued parameter
    @OrderID    INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        IF NOT EXISTS (SELECT 1 FROM @Lines)
            THROW 50010, 'An order must contain at least one line.', 1;

        BEGIN TRANSACTION;

            DECLARE @Inserted TABLE (OrderID INT);

            INSERT INTO dbo.Orders (CustomerID, StoreID, OrderDate, TotalAmount, Status)
            OUTPUT inserted.OrderID INTO @Inserted (OrderID)
            SELECT @CustomerID, @StoreID, SYSUTCDATETIME(),
                   SUM(l.Quantity * p.UnitPrice), 'New'
            FROM   @Lines AS l
            JOIN   dbo.Product AS p ON p.ProductID = l.ProductID;

            SELECT @OrderID = OrderID FROM @Inserted;

            INSERT INTO dbo.OrderLine (OrderID, ProductID, Quantity, LineAmount)
            SELECT @OrderID, l.ProductID, l.Quantity, l.Quantity * p.UnitPrice
            FROM   @Lines AS l
            JOIN   dbo.Product AS p ON p.ProductID = l.ProductID;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;
GO

-- The table type the TVP uses
CREATE TYPE dbo.OrderLineType AS TABLE
(
    ProductID INT NOT NULL,
    Quantity  INT NOT NULL
);
GO

-- Upsert without MERGE (MERGE has known concurrency bugs; this pattern is safer)
CREATE OR ALTER PROCEDURE dbo.usp_UpsertCustomer
    @CustomerID   INT,
    @CustomerName NVARCHAR(120),
    @City         NVARCHAR(80)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRANSACTION;
        UPDATE dbo.Customer WITH (UPDLOCK, SERIALIZABLE)   -- take the lock before deciding
        SET    CustomerName = @CustomerName, City = @City
        WHERE  CustomerID   = @CustomerID;

        IF @@ROWCOUNT = 0
            INSERT INTO dbo.Customer (CustomerName, City)
            VALUES (@CustomerName, @City);
    COMMIT TRANSACTION;
END;
GO

Views: reporting shapes and access control

A view is a stored SELECT. It does not store data and, by default, does not improve performance — the optimiser expands it inline. Its value is that it hides join complexity, presents a stable contract while the underlying tables change, and lets you grant access to some columns or rows without granting access to the table.

Example · three kinds of view
-- 1. Reporting view: hides the join, exposes a clean shape
CREATE OR ALTER VIEW dbo.vw_OrderSummary
AS
SELECT  o.OrderID,
        o.OrderDate,
        o.StoreID,
        c.CustomerID,
        c.CustomerName,
        c.City,
        o.TotalAmount,
        o.Status
FROM    dbo.Orders   AS o
JOIN    dbo.Customer AS c ON c.CustomerID = o.CustomerID;
GO

-- 2. Security view: no email exposed, and only this user's stores.
--    Grant SELECT on the view, deny nothing on the base table.
CREATE OR ALTER VIEW dbo.vw_StoreOrders_Restricted
AS
SELECT o.OrderID, o.OrderDate, o.StoreID, o.TotalAmount, o.Status
FROM   dbo.Orders AS o
JOIN   dbo.StoreAccess AS sa ON sa.StoreID = o.StoreID
WHERE  sa.LoginName = ORIGINAL_LOGIN();
GO
GRANT SELECT ON dbo.vw_StoreOrders_Restricted TO StoreManagerRole;

-- 3. Indexed (materialised) view: physically stored and maintained by the engine.
--    Requires SCHEMABINDING, COUNT_BIG(*), deterministic expressions, no outer joins,
--    no subqueries, and the correct SET options at creation time.
CREATE OR ALTER VIEW dbo.vw_StoreDailyRevenue
WITH SCHEMABINDING
AS
SELECT  o.StoreID,
        CAST(o.OrderDate AS DATE) AS SalesDate,
        SUM(o.TotalAmount)        AS Revenue,
        COUNT_BIG(*)              AS OrderCount     -- mandatory for indexed views
FROM    dbo.Orders AS o                             -- two-part name is mandatory
GROUP BY o.StoreID, CAST(o.OrderDate AS DATE);
GO

CREATE UNIQUE CLUSTERED INDEX IX_vw_StoreDailyRevenue
    ON dbo.vw_StoreDailyRevenue (StoreID, SalesDate);
GO
-- On Enterprise/Azure SQL the optimiser can now use this view automatically,
-- even for queries written against dbo.Orders. On Standard Edition add
-- OPTION (EXPAND VIEWS) awareness or reference the view with WITH (NOEXPAND).

View traps

  • Views on views on views. Three layers deep, the optimiser is expanding dozens of joins to fetch two columns. Flatten them.
  • ORDER BY in a view is not honoured unless you also use TOP, and even then order is not guaranteed. Sort in the outer query.
  • SELECT * in a view freezes the column list at creation time; a new base column does not appear until you run sp_refreshview.
  • Indexed views cost writes. Every insert into Orders now maintains the aggregate too. Great for read-heavy reporting, bad on a hot OLTP path.

Functions: the single biggest performance decision in this module

TypeShapeOptimiser behaviourVerdict
Scalar UDF Returns one value Historically executed once per row, opaque to the optimiser, forces a serial plan. SQL Server 2019+ can inline some of them (Froid), but many are ineligible. Avoid in SELECT/WHERE over large tables
Inline TVF Single RETURN (SELECT ...) Expanded into the calling query like a parameterised view; full cost-based optimisation Preferred

Example · the same requirement three ways
-- BAD: scalar UDF called once per row of Orders
CREATE OR ALTER FUNCTION dbo.fn_CustomerCity_Scalar (@CustomerID INT)
RETURNS NVARCHAR(80)
AS
BEGIN
    DECLARE @City NVARCHAR(80);
    SELECT @City = City FROM dbo.Customer WHERE CustomerID = @CustomerID;
    RETURN @City;
END;
GO
-- 200,000 hidden lookups, serial plan, and the plan will not show you why
SELECT OrderID, dbo.fn_CustomerCity_Scalar(CustomerID) AS City
FROM   dbo.Orders;

-- GOOD: inline table-valued function - the optimiser sees straight through it
CREATE OR ALTER FUNCTION dbo.fn_OrdersByStore (@StoreID INT, @FromDate DATE)
RETURNS TABLE
AS
RETURN
(
    SELECT o.OrderID, o.OrderDate, o.CustomerID, o.TotalAmount, o.Status
    FROM   dbo.Orders AS o
    WHERE  o.StoreID   = @StoreID
      AND  o.OrderDate >= @FromDate
);
GO

SELECT s.OrderID, s.TotalAmount, c.CustomerName
FROM   dbo.fn_OrdersByStore(3, '20260101') AS s
JOIN   dbo.Customer AS c ON c.CustomerID = s.CustomerID;

-- ALSO GOOD: just join. Most scalar UDFs are a join wearing a costume.
SELECT o.OrderID, c.City
FROM   dbo.Orders   AS o
JOIN   dbo.Customer AS c ON c.CustomerID = o.CustomerID;

-- Multi-statement TVF: justified when several steps are genuinely needed
CREATE OR ALTER FUNCTION dbo.fn_StoreScorecard (@FromDate DATE)
RETURNS @Result TABLE
(
    StoreID INT PRIMARY KEY, Revenue DECIMAL(18,2), Orders INT, Band VARCHAR(10)
)
AS
BEGIN
    INSERT INTO @Result (StoreID, Revenue, Orders, Band)
    SELECT StoreID, SUM(TotalAmount), COUNT(*), NULL
    FROM   dbo.Orders WHERE OrderDate >= @FromDate
    GROUP BY StoreID;

    UPDATE @Result
    SET Band = CASE WHEN Revenue > 5000000 THEN 'Gold'
                    WHEN Revenue > 1000000 THEN 'Silver'
                    ELSE 'Bronze' END;
    RETURN;
END;
GO

Triggers: powerful, invisible, easy to misuse

A trigger runs inside the transaction of the statement that fired it. Two rules cover most trigger bugs. First, inserted and deleted are sets, not rows — an UPDATE touching 5,000 rows fires the trigger once with 5,000 rows in inserted. Second, everything the trigger does is on the caller's clock, so slow trigger logic becomes slow inserts everywhere.

Example · a correct set-based audit trigger, and an INSTEAD OF trigger
CREATE TABLE dbo.OrderAudit
(
    OrderAuditID INT IDENTITY(1,1) PRIMARY KEY,
    OrderID      INT           NOT NULL,
    Action       VARCHAR(10)   NOT NULL,
    OldStatus    VARCHAR(20)   NULL,
    NewStatus    VARCHAR(20)   NULL,
    OldAmount    DECIMAL(12,2) NULL,
    NewAmount    DECIMAL(12,2) NULL,
    ChangedBy    SYSNAME       NOT NULL DEFAULT SUSER_SNAME(),
    ChangedUtc   DATETIME2(3)  NOT NULL DEFAULT SYSUTCDATETIME()
);
GO

CREATE OR ALTER TRIGGER dbo.trg_Orders_Audit
ON dbo.Orders
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;                       -- always, in every trigger

    IF NOT EXISTS (SELECT 1 FROM inserted) AND NOT EXISTS (SELECT 1 FROM deleted)
        RETURN;                           -- fired by a 0-row statement, do nothing

    /* One set-based statement handles INSERT, UPDATE and DELETE together. */
    INSERT INTO dbo.OrderAudit (OrderID, Action, OldStatus, NewStatus, OldAmount, NewAmount)
    SELECT  COALESCE(i.OrderID, d.OrderID),
            CASE WHEN i.OrderID IS NOT NULL AND d.OrderID IS NOT NULL THEN 'UPDATE'
                 WHEN i.OrderID IS NOT NULL                            THEN 'INSERT'
                 ELSE 'DELETE' END,
            d.Status, i.Status,
            d.TotalAmount, i.TotalAmount
    FROM        inserted AS i
    FULL JOIN   deleted  AS d ON d.OrderID = i.OrderID
    WHERE       i.OrderID IS NULL           -- deletes
       OR       d.OrderID IS NULL           -- inserts
       OR       EXISTS (SELECT i.Status, i.TotalAmount
                        EXCEPT
                        SELECT d.Status, d.TotalAmount);   -- NULL-safe change detection
END;
GO

-- INSTEAD OF trigger: make a multi-table view updatable
CREATE OR ALTER TRIGGER dbo.trg_vwOrderSummary_Update
ON dbo.vw_OrderSummary
INSTEAD OF UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    IF UPDATE(Status)                        -- only act if that column was targeted
        UPDATE o
        SET    o.Status = i.Status
        FROM   dbo.Orders AS o
        JOIN   inserted   AS i ON i.OrderID = o.OrderID;

    IF UPDATE(CustomerName)
        UPDATE c
        SET    c.CustomerName = i.CustomerName
        FROM   dbo.Customer AS c
        JOIN   inserted     AS i ON i.CustomerID = c.CustomerID;
END;
GO

-- Emergency controls every DBA should know
ALTER TABLE dbo.Orders DISABLE TRIGGER dbo.trg_Orders_Audit;
ALTER TABLE dbo.Orders ENABLE  TRIGGER dbo.trg_Orders_Audit;

-- Find every trigger in the database and whether it is enabled
SELECT  OBJECT_SCHEMA_NAME(t.parent_id) AS SchemaName,
        OBJECT_NAME(t.parent_id)        AS TableName,
        t.name                          AS TriggerName,
        t.is_disabled, t.is_instead_of_trigger
FROM    sys.triggers AS t
WHERE   t.parent_class = 1
ORDER BY TableName, TriggerName;

Modern alternatives to audit triggers. Before you write one, check whether temporal tables (SYSTEM_VERSIONING = ON) or Change Data Capture already give you history for free, maintained by the engine and far cheaper than hand-written triggers. Triggers remain the right answer for enforcing cross-table rules that constraints cannot express.

Example · temporal table instead of an audit trigger
ALTER TABLE dbo.Product ADD
    SysStartTime DATETIME2(3) GENERATED ALWAYS AS ROW START HIDDEN
        CONSTRAINT DF_Product_Start DEFAULT SYSUTCDATETIME(),
    SysEndTime   DATETIME2(3) GENERATED ALWAYS AS ROW END   HIDDEN
        CONSTRAINT DF_Product_End   DEFAULT CONVERT(DATETIME2(3), '9999-12-31 23:59:59.999'),
    PERIOD FOR SYSTEM_TIME (SysStartTime, SysEndTime);

ALTER TABLE dbo.Product
    SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.ProductHistory));

-- What did this product cost on 1 March 2026?
SELECT ProductID, ProductName, UnitPrice
FROM   dbo.Product FOR SYSTEM_TIME AS OF '2026-03-01T00:00:00'
WHERE  ProductID = 42;

Deployment and version control for database objects

  • Everything is a file in Git. One object per file, folder per schema, reviewed in pull requests exactly like C# or Python.
  • Write idempotent scripts. CREATE OR ALTER for procedures, views, functions and triggers; guarded IF NOT EXISTS blocks for tables and columns.
  • Pick a migration model and stick to it. State-based (SSDT / DACPAC: you keep the desired schema, a tool computes the diff) or migration-based (Flyway, Liquibase, DbUp: you keep an ordered list of change scripts). Migration-based is easier to reason about for data changes.
  • Never edit objects in production through SSMS. The next deployment silently overwrites your fix.
  • Test on a restored copy of production-shaped data before release, and always ship a rollback script.
Example · idempotent migration script
/* V014__add_order_channel.sql  -- migration-based deployment */
SET XACT_ABORT ON;
BEGIN TRANSACTION;

IF NOT EXISTS (SELECT 1 FROM sys.columns
               WHERE object_id = OBJECT_ID('dbo.Orders') AND name = 'Channel')
BEGIN
    ALTER TABLE dbo.Orders
        ADD Channel VARCHAR(20) NOT NULL
            CONSTRAINT DF_Orders_Channel DEFAULT 'Store';   -- metadata-only in 2016+
END;

IF NOT EXISTS (SELECT 1 FROM sys.indexes
               WHERE name = 'IX_Orders_Channel_OrderDate'
                 AND object_id = OBJECT_ID('dbo.Orders'))
BEGIN
    CREATE NONCLUSTERED INDEX IX_Orders_Channel_OrderDate
        ON dbo.Orders (Channel, OrderDate) INCLUDE (TotalAmount);
END;

COMMIT TRANSACTION;
GO

/* Procedures are always CREATE OR ALTER - safe to run any number of times. */
CREATE OR ALTER PROCEDURE dbo.usp_GetOrdersByChannel
    @Channel VARCHAR(20)
AS
BEGIN
    SET NOCOUNT ON;
    SELECT OrderID, OrderDate, TotalAmount
    FROM   dbo.Orders
    WHERE  Channel = @Channel;
END;
GO

Common mistakes and pitfalls

  • Row-at-a-time triggers. Writing SELECT @OrderID = OrderID FROM inserted works in testing with one row and corrupts data on the first bulk update.
  • Scalar UDFs in WHERE clauses. They make the predicate non-SARGable and force a scan (Module 4 covers this in depth).
  • Swallowing errors. A CATCH block that only logs and returns 0 turns a failure into silent data loss. Always THROW.
  • Business logic inside triggers. Sending mail, calling xp_cmdshell or writing to a linked server from a trigger holds the caller's transaction open across a network.
  • Nested/recursive triggers firing each other. Check TRIGGER_NESTLEVEL(), and know that RECURSIVE_TRIGGERS is off by default for a reason.
  • SET NOCOUNT OFF in triggers — extra rowcount messages break some ORMs and drivers.
  • Granting table permissions when you meant to grant only EXECUTE on procedures, losing the security benefit entirely.
  • Dynamic SQL built by string concatenation inside procedures — an injection hole. Use sp_executesql with parameters and QUOTENAME() for identifiers.
Example · safe dynamic SQL
-- UNSAFE: @SortColumn and @City are concatenated straight in
-- SET @sql = 'SELECT * FROM dbo.Customer WHERE City = ''' + @City + ''' ORDER BY ' + @SortColumn;

-- SAFE: values are parameters; identifiers are whitelisted and quoted
CREATE OR ALTER PROCEDURE dbo.usp_SearchCustomers
    @City       NVARCHAR(80),
    @SortColumn SYSNAME = N'CustomerName'
AS
BEGIN
    SET NOCOUNT ON;

    IF @SortColumn NOT IN (N'CustomerName', N'City', N'CreatedUtc')
        THROW 50020, 'Invalid sort column.', 1;

    DECLARE @sql NVARCHAR(MAX) =
        N'SELECT CustomerID, CustomerName, City
          FROM   dbo.Customer
          WHERE  (@pCity IS NULL OR City = @pCity)
          ORDER BY ' + QUOTENAME(@SortColumn) + N';';

    EXEC sys.sp_executesql @sql,
         N'@pCity NVARCHAR(80)',
         @pCity = @City;
END;
GO

Practical exercises

  1. Harden a procedure (50 min) Start from the bare usp_GetOrdersByCustomer in the syllabus. Add input validation, optional date parameters, an output row count, an ErrorLog insert and a THROW. Prove the error path by passing @CustomerID = -1 and by forcing a divide-by-zero; confirm a row lands in ErrorLog and the caller still receives the error.
  2. Scalar vs. inline function benchmark (45 min) Write both fn_CustomerCity_Scalar and an equivalent inline TVF/join. Run each over all 200,000 orders with SET STATISTICS TIME, IO ON and actual execution plans on. Record elapsed time, CPU time and whether the plan went parallel. Present the ratio to the class — expect one to two orders of magnitude.
  3. Set-based trigger test (40 min) Implement trg_Orders_Audit. Then run UPDATE dbo.Orders SET Status = 'Closed' WHERE StoreID = 3; (thousands of rows) and verify the audit table received one row per changed order. Deliberately write a broken row-at-a-time version first so learners see the difference.
  4. Deployment dry run (35 min) Package the module's objects as numbered migration scripts. Run them twice in a row on a clean database to prove idempotency, then write the matching rollback script for each. Commit the set to a Git branch and open a pull request for peer review.

Key takeaways

  • Every procedure: SET NOCOUNT ON, XACT_ABORT ON, validation, TRY/CATCH, log then THROW.
  • Views simplify and secure; they do not speed anything up unless they are indexed — and indexed views tax every write.
  • Inline table-valued functions are the safe default; scalar UDFs on large tables are a performance bug waiting to be found.
  • inserted and deleted are always sets. Write set-based trigger logic or expect data corruption.
  • Prefer temporal tables or CDC over hand-rolled audit triggers when you only need history.
  • Database objects belong in Git with idempotent, reviewable, reversible migration scripts.

SQL Server Agent Jobs and Automation

Unattended work you can trust — and diagnose at 3 a.m.
4 hours Lecture + Lab

Learning objectives

  • Create a job end to end — steps, schedules, operators, retry and failure notification — from both SSMS and T-SQL.
  • Configure Database Mail and alerts so a failure reaches a human without anybody watching a screen.
  • Read job history, job step output files and the SQL Server error log to find the real cause of a failure.
  • Automate routine maintenance — index rebuilds, statistics updates, backups, log cleanup — on a sensible schedule.
  • Explain what changes in Azure SQL Database, where SQL Agent does not exist, and pick the right replacement.

Key concepts

The moving parts

SQL Server Agent is a separate Windows service that reads its definitions from msdb. Five objects matter:

  • Job — the container. Owned by a login; owner matters for permissions.
  • Job step — one unit of work (T-SQL, PowerShell, SSIS package, CmdExec). Each step has its own on-success and on-failure action, retry count and retry interval.
  • Schedule — when it runs. Schedules can be shared by several jobs.
  • Operator — a notification target: a name plus an email address.
  • Alert — fires on an error number, a severity level, or a performance counter threshold, and can notify an operator or start a job.
Job anatomy

  (Nightly 01:00)│
                 ▼
            ┌──────────────────────── Job: "Nightly Maintenance" ─────────────────────────┐

USE msdb;
GO

/* ---------- 1. Operator: who gets told ---------- */

    EXEC msdb.dbo.sp_delete_job @job_name = N'RetailDemo - Nightly Maintenance';

EXEC msdb.dbo.sp_add_job
     @job_name               = N'RetailDemo - Nightly Maintenance',
     @description            = N'Stats, index maintenance and log backup for RetailDemo.',
     @owner_login_name       = N'sa',
     @notify_level_email     = 2,            -- 1 = on success, 2 = on failure, 3 = always
     @notify_email_operator_name = N'DBA Team';

/* ---------- 3. Steps ---------- */
EXEC msdb.dbo.sp_add_jobstep
     @job_name     = N'RetailDemo - Nightly Maintenance',
     @step_name    = N'01 - Update statistics',
     @step_id      = 1,
     @subsystem    = N'TSQL',
     @database_name= N'RetailDemo',
     @command      = N'EXEC sys.sp_updatestats;',
     @retry_attempts = 1,
     @retry_interval = 5,                    -- minutes
     @on_success_action = 3,                 -- 3 = go to next step
     @on_fail_action    = 2;                 -- 2 = quit with failure

EXEC msdb.dbo.sp_add_jobstep
     @job_name     = N'RetailDemo - Nightly Maintenance',
     @step_name    = N'02 - Index maintenance',
     @step_id      = 2,
     @subsystem    = N'TSQL',
     @database_name= N'RetailDemo',
     @command      = N'EXEC dbo.usp_IndexMaintenance @ReorganizeThreshold = 5, @RebuildThreshold = 30;',
     @output_file_name = N'C:\SQLLogs\IndexMaint_$(ESCAPE_SQUOTE(JOBID))_$(STEPID).txt',
     @flags        = 2,                      -- append to output file
     @on_success_action = 3,
     @on_fail_action    = 3;                 -- keep going: a failed rebuild must not skip the backup

EXEC msdb.dbo.sp_add_jobstep
     @job_name     = N'RetailDemo - Nightly Maintenance',
     @step_name    = N'03 - Transaction log backup',
     @step_id      = 3,
     @subsystem    = N'TSQL',
     @database_name= N'RetailDemo',

                       TO DISK = N''C:\SQLBackups\RetailDemo_log.trn''
                       WITH COMPRESSION, CHECKSUM, INIT;',
     @on_success_action = 1,                 -- 1 = quit with success
     @on_fail_action    = 2;

/* ---------- 4. Schedule ---------- */
EXEC msdb.dbo.sp_add_jobschedule
     @job_name        = N'RetailDemo - Nightly Maintenance',
     @name            = N'Daily 01:00',
     @freq_type       = 4,                   -- 4 = daily
     @freq_interval   = 1,
     @active_start_time = 010000;            -- HHMMSS

/* ---------- 5. Attach to the local Agent and enable ---------- */
EXEC msdb.dbo.sp_add_jobserver
     @job_name = N'RetailDemo - Nightly Maintenance',
     @server_name = N'(LOCAL)';
GO

The job history viewer in SSMS shows one row per step. Expand the failed step and read the message — the top-level "the job failed" line never contains the cause. If the step writes to an output file, that file usually has more detail than msdb keeps.

Failure triage order

  1. Job history → the step that failed, and its message.
  2. The step's output file, if configured (configure one for every non-trivial step).
  3. SQL Server error log (xp_readerrorlog) around that timestamp.
  4. Windows Event Log / Agent log for service, permission and proxy problems.
  5. Reproduce the step's command manually as the job owner or proxy account — most "it works for me" failures are permission differences.

Automating routine maintenance

Do not blanket-rebuild every index every night; that generates enormous log volume and can be slower than doing nothing. Use fragmentation thresholds, and let statistics maintenance run more often than index maintenance.

Example · threshold-based index maintenance procedure
CREATE OR ALTER PROCEDURE dbo.usp_IndexMaintenance
    @ReorganizeThreshold FLOAT = 5,    -- % fragmentation: reorganize above this
    @RebuildThreshold    FLOAT = 30,   -- % fragmentation: rebuild above this
    @MinPageCount        INT   = 1000, -- ignore tiny indexes; maintenance will not help
    @Online              BIT   = 0     -- 1 requires Enterprise / Azure SQL
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @sql NVARCHAR(MAX), @schema SYSNAME, @table SYSNAME, @index SYSNAME, @frag FLOAT;

    DECLARE cur CURSOR LOCAL FAST_FORWARD FOR      -- a cursor is fine for DDL orchestration
        SELECT  s.name, t.name, i.name, ps.avg_fragmentation_in_percent
        FROM    sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') AS ps
        JOIN    sys.indexes AS i ON i.object_id = ps.object_id AND i.index_id = ps.index_id
        JOIN    sys.tables  AS t ON t.object_id = i.object_id
        JOIN    sys.schemas AS s ON s.schema_id = t.schema_id
        WHERE   ps.avg_fragmentation_in_percent >= @ReorganizeThreshold
          AND   ps.page_count >= @MinPageCount
          AND   i.index_id > 0                     -- skip heaps
          AND   i.is_disabled = 0;

    OPEN cur;
    FETCH NEXT FROM cur INTO @schema, @table, @index, @frag;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        SET @sql = N'ALTER INDEX ' + QUOTENAME(@index) + N' ON '
                 + QUOTENAME(@schema) + N'.' + QUOTENAME(@table)
                 + CASE WHEN @frag >= @RebuildThreshold
                        THEN N' REBUILD' + CASE WHEN @Online = 1 THEN N' WITH (ONLINE = ON)' ELSE N'' END
                        ELSE N' REORGANIZE' END + N';';

        PRINT CONVERT(VARCHAR(30), SYSUTCDATETIME(), 126) + ' ' + @sql;   -- lands in the output file
        BEGIN TRY
            EXEC sys.sp_executesql @sql;
        END TRY
        BEGIN CATCH
            PRINT '  FAILED: ' + ERROR_MESSAGE();      -- keep going with the next index
        END CATCH

        FETCH NEXT FROM cur INTO @schema, @table, @index, @frag;
    END

    CLOSE cur; DEALLOCATE cur;

    /* Statistics: cheaper and more valuable than index maintenance. Run daily. */
    EXEC sys.sp_updatestats;
END;
GO

Common mistakes and pitfalls

  • A job with no failure notification. It will fail one night and nobody will know until the report is wrong.
  • Database Mail configured but Agent never restarted, so alerts silently go nowhere. Always send a test mail.
  • Job owned by a personal login. When that person leaves and the account is disabled, every job stops. Own jobs with sa or a dedicated service account.
  • Overlapping schedules — a job scheduled every 5 minutes that takes 7 minutes will pile up. Guard with a check on sp_help_job @execution_status = 1.
  • Nightly rebuild of every index, generating gigabytes of log and blowing out log backups and Always On replication.
  • No output files, so the only evidence of a failure is a truncated message in msdb.
  • Never purging msdb history until it is tens of gigabytes and the Agent UI takes minutes to open.
  • Assuming Agent exists in Azure SQL Database. It does not. Design for Elastic Jobs or Functions from the start.
  • Storing passwords in job step commands. Use a proxy account with credentials, or pull the secret from Key Vault.

Practical exercises

  1. Build the nightly job (45 min) Script the full three-step maintenance job above, including operator and schedule. Run it, then deliberately break step 2 (reference a non-existent procedure) and confirm the job continues to step 3, still reports failure overall, and sends the notification.
  2. Failure forensics (40 min) The instructor plants three broken jobs: one with a permission error, one with a syntax error, one that times out. Learners must diagnose each using only sysjobhistory, the output file and xp_readerrorlog — and write a one-line root cause for each.
  3. Alerting drill (30 min) Configure Database Mail, send a test message, then create the severity 17–25 and error 823/824/825 alerts. Raise a test error with RAISERROR('Test alert', 17, 1) WITH LOG; and confirm the mail arrives.
  4. Azure equivalent (35 min) Take the same maintenance procedure and schedule it against an Azure SQL Database using either an Elastic Job or a timer-triggered Azure Function. Compare the two on setup effort, monitoring and cost, and write a two-line recommendation.

Key takeaways

  • Job, step, schedule, operator, alert — five objects, all stored in msdb, all scriptable.
  • A job without a notified operator is not automation; it is a time bomb.
  • The failure cause is in the step message and the output file, never in the job-level message.
  • Maintain indexes by threshold, update statistics daily, and run DBCC CHECKDB weekly.
  • Azure SQL Database has no Agent — use Elastic Jobs, Functions or Logic Apps instead.

Query Optimization

From "it's slow" to a measured, defensible fix
8 hours Lecture + Lab

Learning objectives

  • Read estimated and actual execution plans, and find the operator that actually costs the time.
  • Recognise expensive patterns on sight: scans where a seek was possible, key lookups, sorts and hash spills.
  • Explain what statistics and cardinality estimates are, when they go stale, and how to update them safely.
  • Rewrite non-SARGable predicates into a form the optimiser can seek on, and spot implicit conversion.
  • Diagnose parameter sniffing and choose an appropriate mitigation rather than a superstition.
  • Use Query Store to find regressions and force a known-good plan.

Key concepts

How a query becomes a plan

Query lifecycle
  T-SQL text
      │
      ▼
  Parse ──▶ Bind (resolve objects) ──▶ Optimize ──▶ Execute
                                          │             │
                          uses STATISTICS ┘             └──▶ Actual rows, actual time
                          to estimate row counts             (compare to estimates!)
                                          │
                                    Plan Cache ◀── reused for the next matching text

The optimiser is cost-based: it estimates how many rows each step will produce, prices the alternatives and picks the cheapest within a time budget. Almost every bad plan traces back to a bad row estimate. So the first question when reading a plan is never "which operator is red" — it is "where do estimated and actual rows diverge?"

Reading a plan

  • Read right to left, top to bottom. Data flows from the right-hand leaf operators toward the SELECT on the left.
  • Arrow thickness = rows. A fat arrow feeding a small result means you are reading far more than you return.
  • Cost percentages are estimates, even in an "actual" plan. Trust actual rows, actual reads and elapsed time over the cost percentage.
  • Warnings matter. The yellow triangle on an operator flags implicit conversion, spills to tempdb, missing join predicates or excessive memory grants. Read them first.

Statistics and cardinality estimation

A statistics object is a histogram (up to 200 steps) plus density information describing how values are distributed in a column. The optimiser uses it to guess row counts. Auto-update fires when roughly SQRT(1000 × rows) modifications have occurred (SQL Server 2016+ with compatibility level 130+), which on a 200-million-row table is still ~450,000 changes — plenty of time to go stale on a hot date column.

Example · inspecting and updating statistics
-- What statistics exist, when were they last updated, how stale are they?
SELECT  OBJECT_NAME(s.object_id) AS TableName,
        s.name                   AS StatName,
        sp.last_updated,
        sp.rows,
        sp.rows_sampled,
        CAST(100.0 * sp.rows_sampled / NULLIF(sp.rows,0) AS DECIMAL(5,2)) AS SampledPct,
        sp.modification_counter,
        sp.steps
FROM    sys.stats AS s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE   s.object_id = OBJECT_ID('dbo.Orders')
ORDER BY sp.last_updated;

-- Look at the actual histogram - this is what the optimiser sees
DBCC SHOW_STATISTICS ('dbo.Orders', 'IX_Orders_OrderDate') WITH HISTOGRAM;

-- Targeted update, full scan, on the one column that matters
UPDATE STATISTICS dbo.Orders (IX_Orders_OrderDate) WITH FULLSCAN;

-- Whole table, sampled (much cheaper on very large tables)
UPDATE STATISTICS dbo.Orders WITH SAMPLE 20 PERCENT;

-- Whole database (this is what sp_updatestats does; safe as a nightly job)
EXEC sys.sp_updatestats;

-- Keep auto-update on, and make it asynchronous so queries do not wait for it
ALTER DATABASE RetailDemo SET AUTO_UPDATE_STATISTICS ON;
ALTER DATABASE RetailDemo SET AUTO_UPDATE_STATISTICS_ASYNC ON;

-- Persist a custom sample rate so auto-update stops reverting to a tiny sample (2016 SP1 CU4+)
UPDATE STATISTICS dbo.Orders (IX_Orders_OrderDate)
    WITH SAMPLE 50 PERCENT, PERSIST_SAMPLE_PERCENT = ON;

Update statistics before you rebuild indexes, not after. An index rebuild already updates that index's statistics with a full scan, so a subsequent UPDATE STATISTICS with a small sample makes them worse. In a maintenance job: statistics on unindexed columns first, index rebuilds second.

SARGability — the highest-value idea in this module

A predicate is SARGable (Search ARGument-able) when the optimiser can use it to seek into an index. The rule is simple: the indexed column must appear alone on one side of the operator. Wrap it in a function, concatenate it, or force a type conversion, and the engine has to evaluate the expression for every row — a scan.

Example · non-SARGable rewrites, one pattern at a time
/* ---------- 1. Function on the column (the syllabus example) ---------- */
-- BAD: YEAR() hides the column from the index
SELECT COUNT(*) FROM dbo.Orders WHERE YEAR(OrderDate) = 2026;
-- GOOD: half-open range. Works for DATE, DATETIME and DATETIME2 alike.
SELECT COUNT(*) FROM dbo.Orders
WHERE OrderDate >= '20260101' AND OrderDate < '20270101';

/* ---------- 2. Arithmetic on the column ---------- */
-- BAD
SELECT * FROM dbo.Orders WHERE TotalAmount * 1.18 > 10000;
-- GOOD: move the maths to the constant side
SELECT * FROM dbo.Orders WHERE TotalAmount > 10000 / 1.18;

/* ---------- 3. Leading wildcard ---------- */
-- BAD: cannot seek, must scan every row
SELECT * FROM dbo.Customer WHERE CustomerName LIKE '%mart';
-- GOOD: trailing wildcard seeks a range
SELECT * FROM dbo.Customer WHERE CustomerName LIKE 'Wal%';
-- If you truly need "contains", use Full-Text Search or a computed reversed column.

/* ---------- 4. Implicit conversion (the silent killer) ---------- */
-- Suppose Customer.Email is VARCHAR(200) and the app sends NVARCHAR.
-- NVARCHAR has higher precedence, so SQL Server converts the COLUMN, not the parameter.
DECLARE @Email NVARCHAR(200) = N'cust17@example.com';
SELECT * FROM dbo.Customer WHERE Email = @Email;   -- index scan + CONVERT_IMPLICIT warning
-- GOOD: match the types (fix the app's parameter, or the column's type)
DECLARE @EmailV VARCHAR(200) = 'cust17@example.com';
SELECT * FROM dbo.Customer WHERE Email = @EmailV;  -- index seek

-- Find every plan in cache suffering implicit conversion
WITH XMLNAMESPACES (DEFAULT 'http://schemas.microsoft.com/sqlserver/2004/07/showplan')
SELECT TOP (25)
       DB_NAME(p.dbid) AS DbName,
       t.text          AS QueryText,
       p.query_plan
FROM   sys.dm_exec_cached_plans AS cp
CROSS APPLY sys.dm_exec_query_plan(cp.plan_handle) AS p
CROSS APPLY sys.dm_exec_sql_text(cp.plan_handle)   AS t
WHERE  p.query_plan.exist('//Warnings/PlanAffectingConvert') = 1;

/* ---------- 5. OR across different columns ---------- */
-- BAD: often scans
SELECT * FROM dbo.Orders WHERE CustomerID = 17 OR StoreID = 3;
-- GOOD: two seeks unioned
SELECT * FROM dbo.Orders WHERE CustomerID = 17
UNION
SELECT * FROM dbo.Orders WHERE StoreID = 3;

/* ---------- 6. ISNULL / COALESCE on the column ---------- */
-- BAD
SELECT * FROM dbo.Orders WHERE ISNULL(Status, 'New') = 'New';
-- GOOD
SELECT * FROM dbo.Orders WHERE Status = 'New' OR Status IS NULL;

/* ---------- 7. When you cannot change the query: a computed column + index ---------- */
ALTER TABLE dbo.Orders ADD OrderYear AS YEAR(OrderDate) PERSISTED;
CREATE NONCLUSTERED INDEX IX_Orders_OrderYear ON dbo.Orders (OrderYear);
-- Now the original YEAR(OrderDate) = 2026 predicate can seek, because the
-- optimiser matches the expression to the persisted computed column.

Key lookups and covering

Example · removing a key lookup
CREATE NONCLUSTERED INDEX IX_Orders_CustomerID ON dbo.Orders (CustomerID);

-- Plan: Index Seek on IX_Orders_CustomerID  →  Key Lookup on PK_Orders (per row!)
SELECT OrderID, OrderDate, TotalAmount, Status
FROM   dbo.Orders
WHERE  CustomerID = 17;

-- Fix: cover the query. Key columns are searched; INCLUDE columns just ride along.
CREATE NONCLUSTERED INDEX IX_Orders_CustomerID_Covering
    ON dbo.Orders (CustomerID)
    INCLUDE (OrderDate, TotalAmount, Status)
    WITH (DROP_EXISTING = ON);
-- Plan is now a single seek. Logical reads typically drop by 10-100x.

Parameter sniffing

When a procedure compiles, SQL Server "sniffs" the parameter values of that first execution and builds a plan optimised for them. That plan is then reused for every later call. If the data is skewed — store 3 has 400 orders, store 12 has 4 million — the plan that suits one is terrible for the other. The symptom is unmistakable: the same procedure is fast for some inputs and slow for others, and restarting or recompiling flips which ones.

Query Store: the flight recorder

Query Store persists query text, every plan a query has had, and runtime statistics per time interval — inside the user database, so it survives restarts and travels with a backup. It is on by default in Azure SQL Database and SQL Server 2022. Turn it on everywhere else; it is the single best tool for answering "it was fast last week."

Example · enable, query and force plans
ALTER DATABASE RetailDemo SET QUERY_STORE = ON;

-- Top 10 queries by total duration in the last 24 hours
SELECT TOP (10)
       q.query_id, p.plan_id,
       qt.query_sql_text,
       SUM(rs.count_executions)                              AS Executions,
       CAST(AVG(rs.avg_duration)/1000.0 AS DECIMAL(10,2))    AS AvgDurationMs,
       CAST(AVG(rs.avg_cpu_time)/1000.0 AS DECIMAL(10,2))    AS AvgCpuMs,
       CAST(AVG(rs.avg_logical_io_reads) AS BIGINT)          AS AvgReads

JOIN   sys.query_store_runtime_stats_interval AS rsi ON rsi.runtime_stats_interval_id = rs.runtime_stats_interval_id
WHERE  rsi.start_time > DATEADD(DAY, -1, SYSDATETIMEOFFSET())
GROUP BY q.query_id, p.plan_id, qt.query_sql_text
ORDER BY AvgDurationMs DESC;

-- Regressions: queries that have more than one plan with very different durations
SELECT   q.query_id,
         COUNT(DISTINCT p.plan_id)                          AS PlanCount,
         MIN(rs.avg_duration)/1000.0                        AS BestMs,
         MAX(rs.avg_duration)/1000.0                        AS WorstMs,
         MAX(rs.avg_duration) / NULLIF(MIN(rs.avg_duration),0) AS RegressionFactor
FROM     sys.query_store_query AS q
JOIN     sys.query_store_plan  AS p  ON p.query_id = q.query_id
JOIN     sys.query_store_runtime_stats AS rs ON rs.plan_id = p.plan_id
GROUP BY q.query_id
HAVING   COUNT(DISTINCT p.plan_id) > 1
     AND MAX(rs.avg_duration) > 5 * MIN(rs.avg_duration)
ORDER BY RegressionFactor DESC;

-- Pin the good plan (the production emergency button)
EXEC sys.sp_query_store_force_plan   @query_id = 42, @plan_id = 7;
-- ...and release it once the real fix ships
EXEC sys.sp_query_store_unforce_plan @query_id = 42, @plan_id = 7;

-- Which plans are currently forced?
SELECT query_id, plan_id, is_forced_plan, force_failure_count, last_force_failure_reason_desc
FROM   sys.query_store_plan
WHERE  is_forced_plan = 1;

A repeatable tuning method — teach this as a checklist

  1. Measure first. Capture duration, CPU and logical reads. Without a baseline you cannot claim an improvement.
  2. Get the actual plan. Find the largest gap between estimated and actual rows.
  3. Check the cheap causes: stale statistics, implicit conversion, a non-SARGable predicate, a missing index, a scalar UDF.
  4. Change one thing. Re-measure. Keep it only if reads and duration both fell.
  5. Check the blast radius. A new index helps this query and taxes every write. Confirm with the workload, not the query.
  6. Record it in Query Store or a tuning log, so the next person knows why the index exists.
Example · missing-index DMVs (use as a hint, never as a script)
SELECT TOP (20)
       CONVERT(DECIMAL(18,2), migs.user_seeks * migs.avg_total_user_cost * migs.avg_user_impact) AS ImpactScore,
       migs.user_seeks, migs.user_scans, migs.last_user_seek,
       'CREATE NONCLUSTERED INDEX IX_' + OBJECT_NAME(mid.object_id) + '_'
         + REPLACE(REPLACE(REPLACE(ISNULL(mid.equality_columns, mid.inequality_columns), ', ', '_'), '[', ''), ']', '')
         + ' ON ' + mid.statement
         + ' (' + ISNULL(mid.equality_columns, '')
         + CASE WHEN mid.equality_columns IS NOT NULL AND mid.inequality_columns IS NOT NULL THEN ', ' ELSE '' END
         + ISNULL(mid.inequality_columns, '') + ')'
         + ISNULL(' INCLUDE (' + mid.included_columns + ')', '') AS SuggestedIndex
FROM   sys.dm_db_missing_index_group_stats AS migs
JOIN   sys.dm_db_missing_index_groups      AS mig ON mig.index_group_handle = migs.group_handle
JOIN   sys.dm_db_missing_index_details     AS mid ON mid.index_handle       = mig.index_handle
WHERE  mid.database_id = DB_ID()
ORDER BY ImpactScore DESC;

/* Treat the output as evidence, not instructions. The DMV does not know about
   your other indexes, it never suggests dropping anything, it ignores write cost,
   and it will happily propose five overlapping indexes on the same table.
   Consolidate by hand before creating anything (Module 5). */

Common mistakes and pitfalls

  • Tuning by cost percentage. The 92%-cost operator may run in 3 ms. Compare estimated vs. actual rows instead.
  • Creating every index the DMV suggests. You end up with 15 indexes on one table and a write workload on its knees.
  • Adding WITH (NOLOCK) or index hints to "fix" performance instead of finding the estimate problem.
  • Testing on an empty dev database. Plans are chosen by row counts — a plan proven on 100 rows tells you nothing about 100 million.
  • Not clearing measurement noise. The first run pays for physical reads; compare warm runs, or use DROPCLEANBUFFERS consistently on a test instance only.
  • Blaming parameter sniffing for everything. Confirm it: a big spread between min_worker_time and max_worker_time for the same plan.
  • Leaving a forced plan in Query Store forever. It becomes an invisible, undocumented dependency. Track and expire them.
  • Rebuilding indexes to "fix" a slow query. It updates statistics as a side effect — which is usually what actually helped. Update statistics first and find out.

Practical exercises

  1. Plan reading drill (50 min) Run five supplied queries against RetailDemo with actual plans on. For each, record the top operator by actual rows, whether estimates matched reality, the logical reads, and one proposed fix. Apply the fixes and produce a before/after table of reads and duration.
  2. SARGability rewrite set (45 min) Take the seven non-SARGable patterns above and rewrite each one. Prove the change with the plan (scan → seek) and the reads count. Then create the persisted computed column and show that the original YEAR() query now seeks without being rewritten.
  3. Parameter sniffing investigation (45 min) Reproduce the skew, capture both the "small" and "large" plans, then implement all three fixes in turn. Measure CPU per execution for each and write a one-paragraph recommendation on which you would ship and why.
  4. Query Store regression hunt (40 min) Enable Query Store, run a workload, then force a bad plan to simulate a regression. Find it with the regression query above, force the good plan, and confirm the improvement in the Query Store reports. Finish by unforcing and documenting what the permanent fix would be.

Key takeaways

  • Bad plans come from bad row estimates. Compare estimated vs. actual rows before anything else.
  • Logical reads is the tuning currency — it is stable across machines and load in a way that duration is not.
  • SARGability: the indexed column stands alone on one side of the operator. No functions, no arithmetic, no type mismatch.
  • Key lookups are fixed by INCLUDE; spills and bad joins are fixed by fixing the estimate.
  • Parameter sniffing is real but diagnosable — look for a wide min/max CPU spread on one plan.
  • Query Store is the flight recorder: it tells you what the plan was last Tuesday and lets you pin it back.

Large Tables and Indexing Strategy

Designing for hundreds of millions of rows
6 hours Lecture + Lab

Learning objectives

  • Explain how the clustered key is embedded in every nonclustered index, and choose one accordingly.
  • Design covering and filtered indexes from a set of query patterns rather than one query at a time.
  • Measure fragmentation and decide between REORGANIZE, REBUILD and doing nothing.
  • Apply table partitioning for manageability — and explain honestly what it does and does not do for performance.
  • Recognise the workloads where a columnstore index changes the order of magnitude, not the percentage.

Key concepts

How the data is physically laid out

Clustered index structure (B-tree)
                        ┌────────── Root page ──────────┐
                        │  1..5000 │ 5001..10000 │ ...  │
                        └────┬─────────────┬────────────┘
                   ┌─────────┘             └─────────┐
            ┌──────▼──────┐                   ┌──────▼──────┐   Intermediate
            │ 1..1200 │…  │                   │ 5001..6100 │…│   levels
            └──────┬──────┘                   └──────┬──────┘
        ┌──────────┴──────────┐             ┌────────┴────────┐
   ┌────▼────┐   ┌────▼────┐  …        ┌────▼────┐   ┌────▼────┐  LEAF LEVEL =
   │ rows    │──▶│ rows    │──▶ … ──▶  │ rows    │──▶│ rows    │  THE TABLE ITSELF
   │ 1-180   │   │ 181-360 │           │5001-5180│   │5181-5360│  (all columns)
   └─────────┘   └─────────┘           └─────────┘   └─────────┘

  A NONCLUSTERED index has the same shape, but its leaf level holds
  only [key columns] + [INCLUDE columns] + [the clustered key, as the row pointer].
                                             ▲
                            This is why a wide clustered key inflates EVERY index.

A table with a clustered index is that index — the leaf level holds the rows. Without one, the table is a heap and nonclustered indexes point via an 8-byte RID. Heaps are fine for staging and bulk-load targets, poor for anything queried by range.

A good clustered key is: narrow, unique, static and ever-increasing.

CandidateAssessment
INT IDENTITY / BIGINT IDENTITYThe default choice. Narrow, unique, increasing, never updated.
DATETIME2 + identityExcellent for append-only event/order tables queried by date range.
Random UNIQUEIDENTIFIER (NEWID())16 bytes and random — causes page splits on every insert and bloats every nonclustered index. Use NEWSEQUENTIALID() or a surrogate BIGINT instead.
Composite natural key (e.g. StoreID, OrderNo, OrderDate)Wide; those bytes are repeated in every nonclustered index and every foreign key.
NVARCHAR business keyAlmost always wrong — wide, and business keys change.

Designing nonclustered indexes for a workload

Column order in a composite index is not cosmetic. The index is sorted by the first key column, then the second within it, and so on — like a phone book sorted by surname then first name. You can seek on a leading prefix; you cannot seek on the second column alone.

  • Equality predicates first, in order of selectivity, then the range/inequality column, then the ORDER BY column.
  • INCLUDE for columns you only return — they sit at the leaf, add no sort overhead, and are not limited to 900/1700-byte key rules.
  • Aim for a handful of wide, general indexes per table rather than a dozen narrow single-column ones.
  • Rule of thumb: a heavily written OLTP table wants roughly 4–6 nonclustered indexes; if you have 15, you have a maintenance problem, not a tuning strategy.
Example · from query patterns to an index set
/* Given these three real query patterns on dbo.Orders:
     Q1: WHERE CustomerID = ? AND OrderDate >= ?   SELECT OrderDate, TotalAmount
     Q2: WHERE StoreID = ? AND Status = 'New'      ORDER BY OrderDate DESC
     Q3: WHERE OrderDate >= ? AND OrderDate < ?    SELECT SUM(TotalAmount) GROUP BY StoreID
*/

-- For Q1: equality column first, range column second, payload included.
CREATE NONCLUSTERED INDEX IX_Orders_CustomerID_OrderDate
    ON dbo.Orders (CustomerID, OrderDate)
    INCLUDE (TotalAmount);

-- For Q2: two equality columns, then the sort column so the Sort operator disappears.
CREATE NONCLUSTERED INDEX IX_Orders_StoreID_Status_OrderDate
    ON dbo.Orders (StoreID, Status, OrderDate DESC)
    INCLUDE (TotalAmount, CustomerID);

-- For Q3: range on the leading column, grouping and aggregate columns included.
CREATE NONCLUSTERED INDEX IX_Orders_OrderDate
    ON dbo.Orders (OrderDate)
    INCLUDE (StoreID, TotalAmount);

/* Note what we did NOT do: create IX_Orders_CustomerID and
   IX_Orders_CustomerID_OrderDate separately. The second covers the first,
   because (CustomerID) is a leading prefix of (CustomerID, OrderDate). */

-- Filtered index: 95% of rows are 'Closed', but we only ever query the open ones.
CREATE NONCLUSTERED INDEX IX_Orders_Open
    ON dbo.Orders (OrderDate, StoreID)
    INCLUDE (CustomerID, TotalAmount)
    WHERE Status IN ('New', 'Shipped');
-- Tiny index, huge selectivity. Caveat: the query's predicate must match the
-- filter, and parameterised predicates often will not match - test it.

-- Unique index as a constraint AND a performance object
CREATE UNIQUE NONCLUSTERED INDEX UX_Customer_Email
    ON dbo.Customer (Email)
    WHERE Email IS NOT NULL;   -- allows many NULLs, enforces uniqueness on the rest

Fragmentation, fill factor and maintenance

Logical fragmentation means the leaf pages are out of physical order — it hurts large range scans on spinning disks and matters far less on SSD/NVMe or in Azure. Page density (how full each page is) matters more: half-empty pages mean twice the I/O and twice the buffer pool for the same rows.

FragmentationActionCharacteristics
< 5%Do nothingMaintenance costs more than it returns
5–30%REORGANIZEAlways online, minimally logged, resumable by cancelling, does not update statistics
> 30%REBUILDOffline by default (Enterprise/Azure can be ONLINE = ON), fully logged, updates statistics with full scan
Example · measuring and fixing fragmentation
-- LIMITED is cheap; use SAMPLED or DETAILED only on a specific suspect index
SELECT  OBJECT_NAME(ps.object_id) AS TableName,
        i.name                    AS IndexName,
        ps.index_type_desc,
        ps.page_count,
        CAST(ps.avg_fragmentation_in_percent AS DECIMAL(5,2)) AS FragPct,
        CAST(ps.avg_page_space_used_in_percent AS DECIMAL(5,2)) AS PageDensityPct,
        CASE WHEN ps.page_count < 1000 THEN 'Too small - ignore'
             WHEN ps.avg_fragmentation_in_percent > 30 THEN 'REBUILD'
             WHEN ps.avg_fragmentation_in_percent > 5  THEN 'REORGANIZE'
             ELSE 'None' END AS Recommendation
FROM    sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') AS ps
JOIN    sys.indexes AS i ON i.object_id = ps.object_id AND i.index_id = ps.index_id
WHERE   ps.index_id > 0
ORDER BY ps.avg_fragmentation_in_percent DESC;

ALTER INDEX IX_Orders_CustomerID_OrderDate ON dbo.Orders REORGANIZE;

ALTER INDEX IX_Orders_CustomerID_OrderDate ON dbo.Orders
    REBUILD WITH (ONLINE = ON, MAXDOP = 4, RESUMABLE = ON, FILLFACTOR = 90,
                  DATA_COMPRESSION = PAGE);

-- Resumable rebuilds: pause during the business day, resume in the window
ALTER INDEX IX_Orders_CustomerID_OrderDate ON dbo.Orders PAUSE;
ALTER INDEX IX_Orders_CustomerID_OrderDate ON dbo.Orders RESUME;

-- Rebuild everything on one table
ALTER INDEX ALL ON dbo.Orders REBUILD WITH (ONLINE = ON);

/* FILLFACTOR guidance
     100 (default) : read-only or ever-increasing key - no wasted space
     90-95         : moderate random inserts/updates in the middle of the key range
     70-80         : GUID keys or heavy mid-range updates - reduces page splits,
                     at the cost of more pages, more I/O and more memory.
   Do not set a low fill factor "just in case": it permanently inflates the index. */

-- Page compression: often 40-70% smaller, and smaller means fewer reads
ALTER TABLE dbo.Orders REBUILD WITH (DATA_COMPRESSION = PAGE);
EXEC sys.sp_estimate_data_compression_savings 'dbo', 'Orders', NULL, NULL, 'PAGE';

Table partitioning

Partitioning splits one table horizontally across multiple filegroups by a partition function, while it still looks like one table to queries. Be honest with learners about what it is for: manageability, not raw speed. The wins are near-instant archival via SWITCH, partition-level rebuilds, and partition elimination on range scans. The losses are complexity, and query plans that get worse if the partition key is not in the predicate.

Partitioned Orders table by month
  dbo.Orders  (one logical table, partitioned on OrderDate)
  ┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
  │  P1      │  P2      │  P3      │  P4      │  P5      │  P6      │
  │ <2026-01 │ 2026-01  │ 2026-02  │ 2026-03  │ 2026-04  │ >=2026-05│
  │ FG_OLD   │ FG_2026  │ FG_2026  │ FG_2026  │ FG_2026  │ FG_2026  │
  └────┬─────┴──────────┴──────────┴──────────┴──────────┴──────────┘
       │  SWITCH OUT (metadata only, milliseconds)
       ▼
  dbo.Orders_Archive_202512  ──▶ back up ──▶ move to cheap storage ──▶ TRUNCATE

  Query: WHERE OrderDate >= '2026-03-01' AND OrderDate < '2026-04-01'
         → partition elimination: only P4 is touched.
  Query: WHERE CustomerID = 17          (no partition key!)
         → all six partitions scanned. Partitioning made this query SLOWER.
Example · full partitioning setup with a sliding window
/* 1. Filegroups (in production put these on separate storage) */
ALTER DATABASE RetailDemo ADD FILEGROUP FG_Orders_2026;
ALTER DATABASE RetailDemo ADD FILE
    (NAME = N'Orders_2026', FILENAME = N'C:\SQLData\Orders_2026.ndf', SIZE = 512MB, FILEGROWTH = 256MB)
    TO FILEGROUP FG_Orders_2026;

/* 2. Partition function: RANGE RIGHT means the boundary value belongs to the
      partition on its right - the natural choice for dates. */
CREATE PARTITION FUNCTION PF_OrderDate_Monthly (DATETIME2(3))
AS RANGE RIGHT FOR VALUES
('20260101','20260201','20260301','20260401','20260501','20260601');

/* 3. Partition scheme: maps each partition to a filegroup */
CREATE PARTITION SCHEME PS_OrderDate_Monthly
AS PARTITION PF_OrderDate_Monthly ALL TO (FG_Orders_2026);

/* 4. Build the table on the scheme. The partition key MUST be part of every
      unique index, including the primary key. */
CREATE TABLE dbo.Orders_Partitioned
(
    OrderID     INT IDENTITY(1,1) NOT NULL,
    CustomerID  INT           NOT NULL,
    StoreID     INT           NOT NULL,
    OrderDate   DATETIME2(3)  NOT NULL,
    TotalAmount DECIMAL(12,2) NOT NULL,
    Status      VARCHAR(20)   NOT NULL,
    CONSTRAINT PK_Orders_Partitioned PRIMARY KEY CLUSTERED (OrderDate, OrderID)
) ON PS_OrderDate_Monthly (OrderDate);

/* Aligned nonclustered index - same scheme, so SWITCH still works */
CREATE NONCLUSTERED INDEX IX_OrdersPart_Customer
    ON dbo.Orders_Partitioned (CustomerID, OrderDate) INCLUDE (TotalAmount)
    ON PS_OrderDate_Monthly (OrderDate);

/* 5. Inspect: rows per partition */
SELECT  p.partition_number,
        prv.value AS UpperBoundary,
        p.rows,
        fg.name   AS FileGroup
FROM    sys.partitions AS p
JOIN    sys.indexes AS i ON i.object_id = p.object_id AND i.index_id = p.index_id
JOIN    sys.partition_schemes  AS psch ON psch.data_space_id = i.data_space_id
JOIN    sys.destination_data_spaces AS dds
          ON dds.partition_scheme_id = psch.data_space_id AND dds.destination_id = p.partition_number
JOIN    sys.filegroups AS fg ON fg.data_space_id = dds.data_space_id
LEFT JOIN sys.partition_range_values AS prv
          ON prv.function_id = psch.function_id AND prv.boundary_id = p.partition_number
WHERE   p.object_id = OBJECT_ID('dbo.Orders_Partitioned') AND p.index_id <= 1
ORDER BY p.partition_number;

/* 6. Sliding window: archive the oldest month in milliseconds.
      The target table must be identical in schema, indexes and filegroup. */
CREATE TABLE dbo.Orders_Archive_202601
(
    OrderID     INT           NOT NULL,
    CustomerID  INT           NOT NULL,
    StoreID     INT           NOT NULL,
    OrderDate   DATETIME2(3)  NOT NULL,
    TotalAmount DECIMAL(12,2) NOT NULL,
    Status      VARCHAR(20)   NOT NULL,
    CONSTRAINT PK_Orders_Archive_202601 PRIMARY KEY CLUSTERED (OrderDate, OrderID)
) ON FG_Orders_2026;

ALTER TABLE dbo.Orders_Partitioned SWITCH PARTITION 2
    TO dbo.Orders_Archive_202601;      -- metadata operation: no data movement

/* 7. Roll the window forward: merge the empty old boundary, split a new one */
ALTER PARTITION FUNCTION PF_OrderDate_Monthly() MERGE RANGE ('20260101');
ALTER PARTITION SCHEME   PS_OrderDate_Monthly  NEXT USED FG_Orders_2026;
ALTER PARTITION FUNCTION PF_OrderDate_Monthly() SPLIT  RANGE ('20260701');

Always split into an empty partition. Splitting a partition that contains rows moves data and takes a SCH-M lock — the whole table is unavailable and the log grows enormously. Keep an empty tail partition and roll forward before data arrives.

Columnstore indexes

Rowstore stores rows together; columnstore stores each column separately, compressed, in rowgroups of about a million rows with per-segment min/max metadata. For analytical queries that scan millions of rows and touch a few columns, this is 10–100× faster and 5–10× smaller — because of segment elimination and batch-mode execution. For "fetch one order by ID", it is worse than a rowstore seek.

Index typeBest forNotes
Clustered columnstoreFact/history tables, data warehouses, archiveBecomes the storage; add nonclustered rowstore indexes for the occasional point lookup
Nonclustered columnstore on a rowstore tableReal-time operational analytics on an OLTP tableReporting hits the columnstore, transactions keep the rowstore. Costs write throughput.
RowstorePoint lookups, short ranges, OLTPStill the default for transactional tables
Example · columnstore in practice
-- Analytical copy of orders as a clustered columnstore
SELECT OrderID, CustomerID, StoreID, OrderDate, TotalAmount, Status
INTO   dbo.OrdersAnalytics
FROM   dbo.Orders;

CREATE CLUSTERED COLUMNSTORE INDEX CCI_OrdersAnalytics ON dbo.OrdersAnalytics;

-- This aggregation runs in batch mode over compressed segments
SELECT   StoreID,
         DATEPART(YEAR, OrderDate)  AS Yr,
         DATEPART(MONTH, OrderDate) AS Mth,
         COUNT_BIG(*)               AS OrderCount,
         SUM(TotalAmount)           AS Revenue
FROM     dbo.OrdersAnalytics
GROUP BY StoreID, DATEPART(YEAR, OrderDate), DATEPART(MONTH, OrderDate)
ORDER BY Revenue DESC;
-- Check the plan: "Actual Execution Mode = Batch", "Columnstore Index Scan",
-- and a segments-skipped count in the operator properties.

-- Real-time operational analytics: keep the OLTP table, add a filtered
-- nonclustered columnstore covering only the warm data.
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Orders_Recent
    ON dbo.Orders (StoreID, OrderDate, TotalAmount, Status)
    WHERE Status = 'Closed';   -- filtered: keeps the hot rows out of it

-- Health check: rowgroup quality. Under ~100k rows per rowgroup means poor
-- compression, usually caused by trickle inserts.
SELECT  OBJECT_NAME(rg.object_id) AS TableName,
        rg.partition_number, rg.row_group_id, rg.state_desc,
        rg.total_rows, rg.deleted_rows,
        CAST(rg.size_in_bytes / 1048576.0 AS DECIMAL(10,2)) AS SizeMB
FROM    sys.dm_db_column_store_row_group_physical_stats AS rg
WHERE   rg.object_id = OBJECT_ID('dbo.OrdersAnalytics')
ORDER BY rg.row_group_id;

-- Too many OPEN/small rowgroups, or >10% deleted rows: reorganize to compress them
ALTER INDEX CCI_OrdersAnalytics ON dbo.OrdersAnalytics
    REORGANIZE WITH (COMPRESS_ALL_ROW_GROUPS = ON);

Common mistakes and pitfalls

  • A random GUID clustered key. Page splits on every insert, 16 wasted bytes in every nonclustered index, and fragmentation that returns the day after you rebuild.
  • One index per query. Twelve overlapping indexes on Orders: every insert writes thirteen structures, and the optimiser now has more bad choices.
  • Single-column indexes on every foreign key "because best practice". Index the FK when you actually join or cascade-delete on it.
  • Rebuilding indexes nightly regardless of fragmentation — huge log generation, and in Always On/Azure it floods the redo queue.
  • Low fill factor everywhere. A fill factor of 70 makes the index 40% larger forever, for a benefit only mid-range-insert tables see.
  • Partitioning to make queries faster. If the partition key is not in the WHERE clause, you have made things worse. Partition for archiving and maintenance.
  • Forgetting the partition key in the primary key. A unique index on a partitioned table must include the partition column, or the table cannot be aligned.
  • Columnstore on an OLTP table with point lookups. Wrong tool; expect regression on singleton reads.
  • Trickle-inserting into columnstore a few rows at a time, producing thousands of tiny rowgroups. Batch to 102,400+ rows or reorganize regularly.
  • Never dropping anything. Unused indexes cost storage, memory, write throughput and backup time. Check dm_db_index_usage_stats and delete with evidence.

Practical exercises

  1. Index design from requirements (50 min) Given six query patterns supplied by the instructor, design the minimum index set that serves all of them. Justify each index in one line, and explicitly list any index you decided not to create and why. Then apply them and confirm every query seeks.
  2. The write-cost experiment (40 min) Time the insert of 100,000 rows into Orders with zero, three and eight nonclustered indexes. Plot the numbers. This single measurement is what makes "indexes are not free" stick.
  3. Partition and switch (45 min) Build Orders_Partitioned, load two years of data, verify partition elimination in a plan for a single-month query, then SWITCH the oldest month out and time it. Compare against DELETE FROM Orders WHERE OrderDate < ... for the same rows.
  4. Columnstore benchmark (40 min) Run the monthly-revenue aggregation over dbo.Orders (rowstore) and dbo.OrdersAnalytics (columnstore). Record duration, CPU, logical reads, execution mode and table size. Then run a single-order lookup on both and explain the reversal.

Key takeaways

  • The clustered key is duplicated in every nonclustered index: narrow, unique, static, ever-increasing.
  • Index order is equality columns, then range, then sort; INCLUDE carries the payload.
  • Design indexes for the workload, not for individual queries — then verify with usage stats and drop what nobody uses.
  • Maintain by threshold; below 5% fragmentation, do nothing. Rebuilds also refresh statistics, reorganizes do not.
  • Partitioning is a manageability feature: near-instant archival via SWITCH, not a general speed-up.
  • Columnstore transforms scan-and-aggregate workloads and hurts point lookups. Match the tool to the access pattern.

Backup, Restore, and Archiving

The only module where being wrong ends a career
5 hours Lecture + Lab

Learning objectives

  • Explain full, differential and transaction log backups, and how they combine into a restore chain.

  • Perform a point-in-time restore, including STOPAT and tail-log backup, without losing committed data.

Key concepts

RPO and RTO drive every decision

TermQuestion it answersControlled by
RPO — Recovery Point Objective"How much data may we lose?"How often you take log backups
RTO — Recovery Time Objective"How long may we be down?"Backup size, restore speed, chain length, differentials

A 15-minute RPO means log backups every 15 minutes and the FULL recovery model — nothing else can deliver it. A 1-hour RTO on a 2 TB database means differentials, fast storage and a rehearsed procedure, because restoring a week of log backups will not finish in an hour.

Backup types and the restore chain

The most common production incident in this module

A database is in FULL recovery, nobody is taking log backups, and the log file grows until the disk is full and the database stops accepting writes. FULL recovery without log backups is worse than SIMPLE: you get all the cost and none of the protection. Either take log backups or switch to SIMPLE — deliberately.

Point-in-time restore, step by step

Example · "someone ran a DELETE without a WHERE at 14:37"
/* STEP 0 - Stop the bleeding. Get everyone out of the database. */
USE master;
ALTER DATABASE RetailDemo SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

/* STEP 1 - TAIL-LOG BACKUP. Do this FIRST, always. It captures every
   transaction since the last scheduled log backup. Skipping it is the
   difference between losing 0 minutes and losing 15. */
BACKUP LOG RetailDemo
TO DISK = N'C:\SQLBackups\RetailDemo_TAIL.trn'
WITH NORECOVERY, CHECKSUM;         -- NORECOVERY leaves the DB restoring
-- If the data files are damaged/missing, add NO_TRUNCATE and drop NORECOVERY.

/* STEP 2 - Restore the last full, leaving the DB ready for more */
RESTORE DATABASE RetailDemo
FROM DISK = N'C:\SQLBackups\RetailDemo_FULL_20260308.bak'
WITH NORECOVERY, REPLACE, STATS = 10;

/* STEP 3 - Restore the most recent differential (skip all earlier ones) */
RESTORE DATABASE RetailDemo
FROM DISK = N'C:\SQLBackups\RetailDemo_DIFF_20260311.bak'
WITH NORECOVERY, STATS = 10;

/* STEP 4 - Every log backup after that differential, in order */
RESTORE LOG RetailDemo FROM DISK = N'C:\SQLBackups\RetailDemo_LOG_20260311_140000.trn' WITH NORECOVERY;
RESTORE LOG RetailDemo FROM DISK = N'C:\SQLBackups\RetailDemo_LOG_20260311_141500.trn' WITH NORECOVERY;
RESTORE LOG RetailDemo FROM DISK = N'C:\SQLBackups\RetailDemo_LOG_20260311_143000.trn' WITH NORECOVERY;

/* STEP 5 - The tail log, stopping one second before the bad statement */
RESTORE LOG RetailDemo
FROM DISK = N'C:\SQLBackups\RetailDemo_TAIL.trn'
WITH STOPAT = '2026-03-11T14:36:59', RECOVERY;    -- RECOVERY = bring it online

Designing an archiving process

Backups protect against loss; archiving controls growth. A table that grows forever eventually makes every backup, restore, index rebuild and CHECKDB slower. Decide four things before you write any code: retention (how long stays hot), destination (archive table, separate database, blob storage), retrieval (how does someone get an 18-month-old order back?) and legal hold (what must never be deleted).

Temporal history tableEngine maintains history; you set a retention policyYou need row versions, not row removal
Stretch to Azure / external tableCold rows live in Azure, queried transparentlyRare, latency-tolerant access to cold data
Example · safe batched archiving procedure
/* Archive table: same shape, cheaper storage, columnstore for compression */
CREATE TABLE dbo.Orders_Archive
(
    OrderID     INT           NOT NULL,
    CustomerID  INT           NOT NULL,
    StoreID     INT           NOT NULL,
    OrderDate   DATETIME2(3)  NOT NULL,
    TotalAmount DECIMAL(12,2) NOT NULL,
    Status      VARCHAR(20)   NOT NULL,
    ArchivedUtc DATETIME2(3)  NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK_Orders_Archive PRIMARY KEY CLUSTERED (OrderID)
);
GO

CREATE OR ALTER PROCEDURE dbo.usp_ArchiveOrders
    @RetentionMonths INT = 24,
    @BatchSize       INT = 5000,
    @MaxRuntimeMin   INT = 30,      -- stop cleanly inside the maintenance window
    @Debug           BIT = 0
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    DECLARE @Cutoff    DATETIME2(3) = DATEADD(MONTH, -@RetentionMonths, SYSUTCDATETIME()),
            @Deadline  DATETIME2(3) = DATEADD(MINUTE, @MaxRuntimeMin, SYSUTCDATETIME()),
            @Moved     INT = 1,
            @TotalMoved BIGINT = 0;

    WHILE @Moved > 0 AND SYSUTCDATETIME() < @Deadline
    BEGIN
        BEGIN TRANSACTION;

            /* DELETE ... OUTPUT moves the rows atomically: one statement,
               one set of locks, no window where a row exists in both tables. */
            DELETE TOP (@BatchSize) o
            OUTPUT deleted.OrderID, deleted.CustomerID, deleted.StoreID,
                   deleted.OrderDate, deleted.TotalAmount, deleted.Status
              INTO dbo.Orders_Archive (OrderID, CustomerID, StoreID, OrderDate, TotalAmount, Status)
            FROM dbo.Orders AS o
            WHERE o.OrderDate < @Cutoff
              AND o.Status = 'Closed'          -- never archive open work
              AND NOT EXISTS (SELECT 1 FROM dbo.LegalHold AS lh WHERE lh.OrderID = o.OrderID);

            SET @Moved = @@ROWCOUNT;
            SET @TotalMoved += @Moved;

        COMMIT TRANSACTION;

        IF @Debug = 1
            RAISERROR('Archived %d rows (total %I64d)', 0, 1, @Moved, @TotalMoved) WITH NOWAIT;

        /* Breathe: let other work through, and let log backups truncate. */
        WAITFOR DELAY '00:00:00.250';
    END

    /* Child rows first in a real system - archive OrderLine BEFORE Orders,
       or the foreign key will block the delete. */
    SELECT @TotalMoved AS RowsArchived;
END;
GO

-- Unified view so reports do not care where a row lives
CREATE OR ALTER VIEW dbo.vw_AllOrders
AS
SELECT OrderID, CustomerID, StoreID, OrderDate, TotalAmount, Status, CAST(0 AS BIT) AS IsArchived
FROM   dbo.Orders
UNION ALL
SELECT OrderID, CustomerID, StoreID, OrderDate, TotalAmount, Status, CAST(1 AS BIT) AS IsArchived
FROM   dbo.Orders_Archive;
GO

Why batches of ~5,000. A single DELETE of ten million rows takes one enormous transaction, escalates to a table lock, blocks everything, generates a log file you cannot back up mid-flight, and rolls back for hours if it fails. Batching keeps each transaction short, lets log backups truncate between batches, and is safely restartable. Stay under the 5,000-lock escalation threshold per transaction where you can.

Common mistakes and pitfalls

  • Never testing a restore. Untested backups fail at exactly the wrong moment. Restore to a scratch server monthly and time it — that is your real RTO.
  • Forgetting the tail-log backup. It converts "we lost 15 minutes" into "we lost nothing".
  • FULL recovery with no log backups. The log grows without bound until the database stops.
  • Shrinking the log file as routine maintenance. It just grows again, fragmenting the VLFs and hurting performance. Shrink only after a genuine one-off event.
  • Backups on the same disk as the data files. One disk failure takes both.
  • No offsite or immutable copy. Ransomware encrypts the backup share too. Use immutable blob storage or an air-gapped copy.
  • Backing up only user databases. Losing master and msdb means rebuilding every login, job and alert by hand.
  • Deleting the archive source before verifying the copy landed. Move rows with a single DELETE ... OUTPUT ... INTO, never delete-then-insert.
  • Archiving parent rows before child rows, so foreign keys block everything mid-run.
  • Assuming Azure's automated backups meet your RPO. Check the retention setting; the default is 7 days, and LTR is off unless you turn it on.
  • Restoring in Azure expecting an in-place overwrite. Azure PITR always creates a new database; plan the rename/cutover step.

Practical exercises

  1. Full point-in-time restore drill (60 min) Take a full backup, generate activity, take a differential and two log backups, then run a destructive DELETE and note the exact time. Recover with zero data loss using the tail-log + STOPAT sequence. Time the whole thing and compare it to a stated 30-minute RTO.
  2. Design to an SLA (40 min) Given: 800 GB database, RPO 5 minutes, RTO 1 hour, 7-year regulatory retention, 20% annual growth. Produce the backup schedule, recovery model, storage layout, retention policy and the Azure equivalent. Defend the differential frequency — that is where most designs fail RTO.
  3. Archiving implementation (45 min) Implement usp_ArchiveOrders including the OrderLine child table in the right order. Run it against the seeded data with a 12-month retention, verify counts reconcile exactly (archived + remaining = original), and confirm vw_AllOrders still returns every historical order.
  4. Break the chain (30 min) Take a log backup with a third-party tool (or a COPY_ONLY misuse), then attempt a point-in-time restore and observe the LSN gap error. Then use the backupset query above to identify exactly where the chain broke.

Key takeaways

  • RPO is set by log-backup frequency; RTO is set by backup size, chain length and rehearsal.
  • Restore order: tail-log first, then full, then the latest differential, then every log in sequence, STOPAT last.
  • FULL recovery without log backups is the worst of all worlds — pick one deliberately.
  • Archive in small batches with DELETE ... OUTPUT ... INTO, children before parents, and keep a unified read view.
  • Azure automates the backups but not the retention decisions, the cutover, or the testing.
  • A backup you have never restored is not a backup. Rehearse quarterly and record the elapsed time.

Key concepts

SQL Server has no native JSON type (Azure SQL Database now offers one; on-premises you use NVARCHAR(MAX)). JSON support is a set of functions over text plus a CHECK (ISJSON(col) = 1) constraint. That is a strength: JSON columns index, back up and replicate like any other column.

FunctionReturnsUse for

JSON_VALUE(expr, path)A scalar (max NVARCHAR(4000))Extract one property

The one rule that prevents most JSON confusion: JSON_VALUE returns scalars and returns NULL if you point it at an object or array; JSON_QUERY returns objects/arrays and returns NULL if you point it at a scalar. They are mirror images, and mixing them up is the most common error in this module.

Shredding JSON with OPENJSON

OPENJSON has two modes. Without WITH, it returns three columns (key, value, type) — useful for exploring unknown payloads. With an explicit WITH schema, it returns typed columns — which is what you use in production.

Example · flattening a nested payload into relational rows
DECLARE @json NVARCHAR(MAX) = (SELECT Payload FROM dbo.OrderPayload WHERE PayloadID = 1);

/* ---- 1. Default schema: explore an unfamiliar payload ---- */
SELECT [key], [value], [type]      -- type: 0=null 1=string 2=int 3=bool 4=array 5=object
FROM   OPENJSON(@json);

/* ---- 2. Explicit schema: header fields, correctly typed ---- */
SELECT *
FROM   OPENJSON(@json)
WITH (
    PosOrderId   VARCHAR(40)  '$.orderId',
    StoreID      INT          '$.storeId',
    CapturedUtc  DATETIME2(3) '$.capturedUtc',
    CustomerID   INT          '$.customer.id',
    CustomerName NVARCHAR(120)'$.customer.name',
    Gross        DECIMAL(12,2)'$.totals.gross',
    LinesJson    NVARCHAR(MAX)'$.lines' AS JSON     -- AS JSON is REQUIRED for objects/arrays
);

/* ---- 3. Header + lines together: CROSS APPLY down the hierarchy ---- */
SELECT  h.PosOrderId, h.StoreID, h.CapturedUtc, h.CustomerID,
        l.LineNo, l.Sku, l.Qty, l.UnitPrice, l.Discount,
        (l.Qty * l.UnitPrice) - l.Discount AS LineAmount
FROM    OPENJSON(@json)
        WITH (
            PosOrderId  VARCHAR(40)  '$.orderId',
            StoreID     INT          '$.storeId',
            CapturedUtc DATETIME2(3) '$.capturedUtc',
            CustomerID  INT          '$.customer.id',
            Lines       NVARCHAR(MAX)'$.lines' AS JSON
        ) AS h
CROSS APPLY OPENJSON(h.Lines)
        WITH (
            Sku       VARCHAR(30)   '$.sku',
            Qty       INT           '$.qty',
            UnitPrice DECIMAL(10,2) '$.unitPrice',
            Discount  DECIMAL(10,2) '$.discount'
        ) AS l
OUTER APPLY (SELECT CAST([key] AS INT) + 1 FROM OPENJSON(h.Lines) WHERE [value] = ( SELECT 1 )) AS ln(LineNo);

/* ---- 4. Simpler ordinal: OPENJSON's [key] IS the array index ---- */
SELECT  CAST(l.[key] AS INT) + 1                      AS LineNo,
        JSON_VALUE(l.[value], '$.sku')                AS Sku,
        CAST(JSON_VALUE(l.[value], '$.qty') AS INT)   AS Qty
FROM    OPENJSON(@json, '$.lines') AS l
ORDER BY LineNo;

/* ---- 5. Bulk insert a whole batch of orders from one JSON document ---- */
DECLARE @batch NVARCHAR(MAX) = N'[

Producing JSON with FOR JSON

Example · from flat rows to a nested API response
/* ---- The syllabus example ---- */
SELECT CustomerID, OrderID, TotalAmount
FROM   dbo.Orders
WHERE  OrderID <= 3
FOR JSON PATH, ROOT('orders');

SELECT TOP (2)
       o.OrderID                AS 'orderId',
       o.OrderDate              AS 'capturedUtc',
       c.CustomerID             AS 'customer.id',
       c.CustomerName           AS 'customer.name',
       c.City                   AS 'customer.city',
       o.TotalAmount            AS 'totals.gross'
FROM   dbo.Orders   AS o
JOIN   dbo.Customer AS c ON c.CustomerID = o.CustomerID
FOR JSON PATH, ROOT('orders');
/* Produces:
   { "orders": [ { "orderId":1, "capturedUtc":"...",
                   "customer": {"id":17,"name":"Customer 17","city":"Pune"},
                   "totals":   {"gross":2450.00} } ] }                        */

/* ---- Nested arrays: a correlated subquery with FOR JSON PATH ---- */
CREATE OR ALTER PROCEDURE dbo.usp_GetOrderJson
    @OrderID INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT  o.OrderID      AS 'orderId',
            o.OrderDate    AS 'capturedUtc',
            o.Status       AS 'status',
            c.CustomerID   AS 'customer.id',
            c.CustomerName AS 'customer.name',
            c.Email        AS 'customer.email',
            o.TotalAmount  AS 'totals.gross',
            (
                SELECT  p.ProductID  AS 'productId',
                        p.ProductName AS 'name',
                        ol.Quantity  AS 'qty',
                        ol.LineAmount AS 'amount'
                FROM    dbo.OrderLine AS ol
                JOIN    dbo.Product   AS p ON p.ProductID = ol.ProductID
                WHERE   ol.OrderID = o.OrderID
                FOR JSON PATH                         -- nested array, no ROOT
            ) AS 'lines'
    FROM    dbo.Orders   AS o
    JOIN    dbo.Customer AS c ON c.CustomerID = o.CustomerID
    WHERE   o.OrderID = @OrderID
    FOR JSON PATH, WITHOUT_ARRAY_WRAPPER;             -- single object, not [ {...} ]
END;
GO

EXEC dbo.usp_GetOrderJson @OrderID = 1;

/* ---- Options cheat sheet ----
   FOR JSON PATH                  dotted aliases control nesting   (use this)
   FOR JSON AUTO                  nesting inferred from the JOINs  (fragile)
   , ROOT('name')                 wraps the array in a named object
   , WITHOUT_ARRAY_WRAPPER        emit a single object instead of an array
   , INCLUDE_NULL_VALUES          keep nulls (omitted by default)
   ---- Gotcha: in SSMS the JSON comes back as ONE column, one row, and the
   grid truncates it. Use "Results to Text" and raise the character limit,
   or SELECT ... INTO a variable, or just read it from the API.            */

/* ---- Return JSON as an OUTPUT parameter (nice for Azure Functions) ---- */
CREATE OR ALTER PROCEDURE dbo.usp_GetOrderJson_Out

AS

CREATE OR ALTER PROCEDURE dbo.usp_PromotePayloads
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    /* 1. Quarantine anything structurally unusable. TRY_CAST everywhere:
          one bad value must not fail the whole batch. */
    INSERT INTO dbo.PayloadQuarantine (PayloadID, Reason, RawPayload)
    SELECT  p.PayloadID,
            CASE WHEN ISJSON(p.Payload) <> 1                        THEN 'Not valid JSON'
                 WHEN JSON_VALUE(p.Payload, '$.orderId')  IS NULL   THEN 'Missing $.orderId'
                 WHEN TRY_CAST(JSON_VALUE(p.Payload,'$.storeId') AS INT) IS NULL
                                                                     THEN 'storeId not numeric'
                 WHEN TRY_CAST(JSON_VALUE(p.Payload,'$.totals.gross') AS DECIMAL(12,2)) IS NULL
                                                                     THEN 'gross not numeric'
                 ELSE 'Unknown' END,
            p.Payload
    FROM    dbo.OrderPayload AS p
    WHERE   p.OrderID IS NULL
      AND ( ISJSON(p.Payload) <> 1
         OR JSON_VALUE(p.Payload, '$.orderId') IS NULL
         OR TRY_CAST(JSON_VALUE(p.Payload,'$.storeId') AS INT) IS NULL
         OR TRY_CAST(JSON_VALUE(p.Payload,'$.totals.gross') AS DECIMAL(12,2)) IS NULL );

    /* 2. Promote the good ones, skipping anything already processed. */
    BEGIN TRANSACTION;

        DECLARE @Promoted TABLE (PayloadID INT, SourceOrderId VARCHAR(40), OrderID INT);

        INSERT INTO dbo.Orders (CustomerID, StoreID, OrderDate, TotalAmount, Status)
        OUTPUT inserted.OrderID, 0, 0 INTO @Promoted (OrderID, PayloadID, SourceOrderId)
        SELECT  COALESCE(TRY_CAST(JSON_VALUE(p.Payload,'$.customer.id') AS INT), 0),
                TRY_CAST(JSON_VALUE(p.Payload,'$.storeId') AS INT),
                COALESCE(TRY_CAST(JSON_VALUE(p.Payload,'$.capturedUtc') AS DATETIME2(3)), p.ReceivedUtc),
                TRY_CAST(JSON_VALUE(p.Payload,'$.totals.gross') AS DECIMAL(12,2)),
                COALESCE(JSON_VALUE(p.Payload,'$.status'), 'New')      -- new optional field: tolerated
        FROM    dbo.OrderPayload AS p
        WHERE   p.OrderID IS NULL
          AND   ISJSON(p.Payload) = 1
          AND   NOT EXISTS (SELECT 1 FROM dbo.PayloadQuarantine q WHERE q.PayloadID = p.PayloadID)
          AND   NOT EXISTS (SELECT 1 FROM dbo.OrderStagingKey k
                            WHERE k.SourceOrderId = JSON_VALUE(p.Payload,'$.orderId'));

    COMMIT TRANSACTION;
END;
GO

/* ---- Schema-drift detection: what keys are we seeing that we do not handle? ---- */
SELECT   j.[key] AS PropertyName, COUNT(*) AS Occurrences, MIN(p.ReceivedUtc) AS FirstSeen
FROM     dbo.OrderPayload AS p
CROSS APPLY OPENJSON(p.Payload) AS j
WHERE    p.ReceivedUtc >= DATEADD(DAY, -7, SYSUTCDATETIME())
GROUP BY j.[key]
ORDER BY FirstSeen DESC;
-- Run this on a schedule. A new property appearing is your early warning that
-- the upstream system changed - long before a report goes wrong. (Module 9.)

Calling out from SQL Server — and why you usually should not

SQL Server can call HTTP endpoints via sp_invoke_external_rest_endpoint (Azure SQL only) or CLR/sp_OACreate (on-premises, legacy). Prefer not to. An outbound call inside a transaction holds locks for the duration of somebody else's network latency. The correct architecture is the one Module 8 builds: the database exposes procedures, and an Azure Function or integration layer does the calling.

Common mistakes and pitfalls

  • JSON_VALUE on an array or object returns NULL, not the fragment. Use JSON_QUERY.
  • Forgetting AS JSON in an OPENJSON ... WITH clause for a nested object — you get NULL, silently.
  • JSON_VALUE truncating at 4000 characters. Long values need JSON_QUERY or OPENJSON.
  • No index on the JSON properties you filter on. Every query then scans and parses every document. Add a persisted computed column.
  • No ISJSON check constraint, so malformed text lands in the table and every downstream query fails.
  • CAST instead of TRY_CAST during ingestion — one bad value kills a 50,000-row batch.
  • Assuming the payload shape is stable. External systems add, rename and re-type fields. Monitor for drift.
  • Storing JSON for data you constantly filter and aggregate on, then wondering why reports are slow. Promote those fields to columns.
  • Building JSON by string concatenation. It breaks on the first quote, newline or non-ASCII character. Use FOR JSON, which escapes correctly.
  • Making outbound HTTP calls inside a transaction, holding locks across the internet.

Key takeaways

  • JSON_VALUE for scalars, JSON_QUERY for objects and arrays, OPENJSON for rowsets, FOR JSON PATH for output.
  • Always guard a JSON column with CHECK (ISJSON(col) = 1).
  • Index JSON properties through persisted computed columns — otherwise every filter is a full scan and parse.
  • Hybrid beats purity: keep the raw payload for provenance, promote the queried fields to typed columns.
  • Ingest defensively — stage first, TRY_CAST everything, quarantine failures with a reason, stay idempotent.
  • Watch for new keys in incoming payloads; schema drift is a scheduled query, not a surprise.
  • Let the application or an Azure Function make HTTP calls, not the database inside a transaction.

using System.Data;
using System.Net;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Azure.Functions.Worker.Http;
using Microsoft.Data.SqlClient;
using Microsoft.Extensions.Logging;

public class OrdersFunction
{
    private readonly ILogger<OrdersFunction> _log;
    private readonly string _cs;

    public OrdersFunction(ILogger<OrdersFunction> log)
    {
        _log = log;
        // Managed identity - NO password anywhere:
        // "Server=tcp:sql-retail.database.windows.net,1433;Database=RetailDemo;
        //  Authentication=Active Directory Default;Encrypt=True;"
        _cs = Environment.GetEnvironmentVariable("SqlConnectionString")!;
    }

    [Function("GetOrder")]
    public async Task<HttpResponseData> GetOrder(
        [HttpTrigger(AuthorizationLevel.Function, "get", Route = "orders/{orderId:int}")]
        HttpRequestData req,
        int orderId)
    {
        // Correlate this call with the APIM request and the SQL dependency
        var correlationId = req.Headers.TryGetValues("x-request-id", out var v)
                            ? v.First() : Guid.NewGuid().ToString();

        using var scope = _log.BeginScope(new Dictionary<string, object>
        {
            ["CorrelationId"] = correlationId,
            ["OrderId"]       = orderId
        });

        try
        {
            await using var conn = new SqlConnection(_cs);
            await conn.OpenAsync();

            await using var cmd = new SqlCommand("dbo.usp_GetOrderJson", conn)
            {
                CommandType    = CommandType.StoredProcedure,
                CommandTimeout = 30                     // fail fast; do not hang the gateway
            };
            cmd.Parameters.Add("@OrderID", SqlDbType.Int).Value = orderId;

            // The procedure returns FOR JSON output as a single nvarchar column
            var json = (string?)await cmd.ExecuteScalarAsync();

            if (string.IsNullOrEmpty(json))
            {
                _log.LogWarning("Order {OrderId} not found", orderId);
                return req.CreateResponse(HttpStatusCode.NotFound);
            }

            var res = req.CreateResponse(HttpStatusCode.OK);
            res.Headers.Add("Content-Type", "application/json; charset=utf-8");
            res.Headers.Add("x-request-id", correlationId);
            await res.WriteStringAsync(json);
            return res;
        }
        catch (SqlException ex) when (ex.Number == -2)          // timeout
        {
            _log.LogError(ex, "SQL timeout retrieving order {OrderId}", orderId);
            return req.CreateResponse(HttpStatusCode.GatewayTimeout);
        }
        catch (SqlException ex) when (ex.Number is 40197 or 40501 or 49918 or 4060 or 40613)
        {
            // Azure SQL transient errors: throttling, busy, or failover in progress
            _log.LogWarning(ex, "Transient SQL error {Number}; client should retry", ex.Number);
            var res = req.CreateResponse(HttpStatusCode.ServiceUnavailable);
            res.Headers.Add("Retry-After", "5");
            return res;
        }
        catch (Exception ex)
        {
            _log.LogError(ex, "Unhandled error retrieving order {OrderId}", orderId);
            return req.CreateResponse(HttpStatusCode.InternalServerError);
        }
    }

    [Function("CreateOrder")]
    public async Task<HttpResponseData> CreateOrder(
        [HttpTrigger(AuthorizationLevel.Function, "post", Route = "orders")]
        HttpRequestData req)
    {
        var body = await new StreamReader(req.Body).ReadToEndAsync();

        await using var conn = new SqlConnection(_cs);
        await conn.OpenAsync();

        // Push the whole payload to SQL and let OPENJSON shred it (Module 7).
        await using var cmd = new SqlCommand("dbo.usp_IngestOrderPayload", conn)
        {
            CommandType = CommandType.StoredProcedure
        };
        cmd.Parameters.Add("@Payload", SqlDbType.NVarChar, -1).Value = body;
        cmd.Parameters.Add("@SourceSystem", SqlDbType.VarChar, 30).Value = "OPOS";
        var outId = cmd.Parameters.Add("@OrderID", SqlDbType.Int);
        outId.Direction = ParameterDirection.Output;

        await cmd.ExecuteNonQueryAsync();

        var res = req.CreateResponse(HttpStatusCode.Created);
        res.Headers.Add("Location", $"/orders/{outId.Value}");
        return res;
    }
}

import json, logging, os
import azure.functions as func
import pyodbc

app = func.FunctionApp(http_auth_level=func.AuthLevel.FUNCTION)

CONN = os.environ["SqlConnectionString"]   # uses ActiveDirectoryMsi authentication

@app.route(route="orders/{order_id:int}", methods=["GET"])
def get_order(req: func.HttpRequest) -> func.HttpResponse:
    order_id = int(req.route_params["order_id"])
    correlation_id = req.headers.get("x-request-id", "")

    try:
        with pyodbc.connect(CONN, timeout=30) as conn:
            cursor = conn.cursor()
            cursor.execute("{CALL dbo.usp_GetOrderJson (?)}", order_id)
            row = cursor.fetchone()

        if not row or not row[0]:
            return func.HttpResponse(status_code=404)

        return func.HttpResponse(
            row[0],
            mimetype="application/json",
            headers={"x-request-id": correlation_id},
        )
    except pyodbc.Error as e:
        logging.exception("SQL error for order %s (corr=%s)", order_id, correlation_id)
        # 40197/40501/49918/4060/40613 are transient in Azure SQL - tell the client to retry
        return func.HttpResponse(status_code=503, headers={"Retry-After": "5"})

Two things that break Functions-to-SQL in production

  1. Connection exhaustion. A Function scales to hundreds of instances; each opens its own pool. Keep Max Pool Size modest, reuse the client across invocations (static or DI-registered), always await using, and prefer short transactions.
  2. No retry on transient errors. Azure SQL will throttle and fail over. Enable SqlClient's built-in retry logic (ConnectRetryCount, or a SqlRetryLogicProvider) and make every write idempotent so a retry cannot double-post.

Application Insights

Application Insights collects requests (inbound calls), dependencies (outbound calls, including every SQL command), traces (your log statements), exceptions and custom metrics. The thing that makes it powerful is operation_Id: every telemetry item from one logical request shares it, so the end-to-end transaction view reconstructs the whole path.

Example · KQL queries you will actually use
// 1. Slowest operations in the last 24 hours, with percentiles that matter
requests
| where timestamp > ago(24h)
| summarize Count = count(),
            P50 = percentile(duration, 50),
            P95 = percentile(duration, 95),
            P99 = percentile(duration, 99),
            FailRate = 100.0 * countif(success == false) / count()
        by operation_Name
| order by P95 desc

// 2. Failure rate over time, five-minute buckets - feed this to a chart on the wall
requests

Common mistakes and pitfalls

  • Connection strings with passwords in app settings. Use managed identity, or Key Vault references at minimum.
  • Exposing the Function URL directly. Callers then bypass every APIM policy. Restrict the Function to APIM's identity or private endpoint.
  • No retry for transient Azure SQL errors (40197, 40501, 40613, 49918, 4060) — and no idempotency, so the retry double-posts.
  • Opening a new SqlConnection per call without pooling discipline, exhausting connections as the Function scales out.
  • Long-running work in an HTTP trigger. Anything over a few seconds belongs on a queue trigger with a 202 + status endpoint.
  • Application Insights sampling left at the default in production, so the one request you need to trace was sampled away — or set to 100% and the bill explodes. Pick deliberately.
  • Alerting on averages. An average hides the P95 that users feel. Alert on percentiles and error rate.
  • No correlation id. Without one flowing gateway → function → SQL, "the API was slow at 14:37" is unanswerable.
  • Caching write operations, or caching without vary-by, returning one customer's data to another.
  • Returning raw exception text to callers, leaking schema names, server names and stack traces.
  • Ignoring cold starts on Consumption when the SLA says 200 ms. Move to Premium with pre-warmed instances.

Key takeaways

  • Functions hold the logic, APIM holds the policy, Application Insights holds the evidence — keep those responsibilities separate.
  • Managed identity removes the entire class of leaked-credential incidents. Use it from day one.
  • Every Azure SQL client needs transient-error retry and idempotent writes; one without the other is a data bug.
  • APIM policies are ordered: authenticate, throttle, validate, correlate, cache, then forward.
  • A correlation id flowing through every hop turns a three-hour investigation into one KQL query.
  • Alert on P95 and error rate, never on averages; and decide sampling deliberately.
  • When the API is slow, the dependency-share query tells you immediately whether it is SQL's fault — then Module 4 takes over.

The architecture

OPOS (OLE for Retail POS) is the device-layer standard the till uses to talk to hardware — scanners, printers, cash drawers. In this course we use "OPOS" as shorthand for the whole in-store point-of-sale application that captures transactions, typically with its own local SQL Server or SQL Express instance so the lane keeps selling when the link is down. Dynamics 365 is the ERP/commerce system of record. The Azure layer moves data between them and exposes it to everything else.

Design decisions, and why

DecisionOptionsRecommendation and reasoning
Store → cloud transport Direct SQL replication; direct API call per sale; store-and-forward outbox Store-and-forward outbox. Replication needs stable connectivity and couples schemas; per-sale API calls fail when the link drops mid-sale. The outbox lets the till commit locally and forward later.
Batching One message per transaction; micro-batches Micro-batches of 50–200 transactions. Per-transaction messages multiply overhead across 500 stores; huge batches make partial failure expensive and retry costly.
Buffer between ingest and processing Direct to database; Service Bus queue; Event Hubs Service Bus queue. It gives durable buffering, per-message retry, dead-lettering and sessions for ordering. Event Hubs is for high-volume telemetry, not transactional messages needing DLQ semantics.
Duplicate protection Trust the sender; dedupe on a natural key; dedupe on a message id Both. Service Bus duplicate detection on MessageId for the transport, plus a unique constraint on (StoreID, TerminalID, TransactionNo, BusinessDate) in the database. Transport dedupe has a time window; the database constraint is permanent.
D365 write path Dual-write; Data Lake export + batch; OData API Depends on volume. OData for low-volume, near-real-time updates; Data Lake export for bulk and analytics; Dual-write for tightly coupled master data. Never write directly to D365 tables.
Clock authority Store local time; cloud arrival time; both Both, in UTC. Keep CapturedUtc (business time, from the till) and ReceivedUtc (arrival). Store clocks drift; you need business time for reporting and arrival time for lag monitoring.
Failure visibility Logs only; dead-letter queue; DLQ + reconciliation job DLQ + a daily reconciliation job. A DLQ nobody watches is a data-loss mechanism with extra steps.

/* The sale and its outbox row commit together. This is the whole point:
   if the sale is committed, the message WILL eventually be sent; if the
   transaction rolls back, no phantom message exists. */
CREATE OR ALTER PROCEDURE dbo.usp_CompleteSale
    @TerminalID INT, @TransactionNo INT, @BusinessDate DATE, @Payload NVARCHAR(MAX)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRANSACTION;
        INSERT INTO dbo.SalesTransaction (TerminalID, TransactionNo, BusinessDate, Payload)
        VALUES (@TerminalID, @TransactionNo, @BusinessDate, @Payload);

        INSERT INTO dbo.Outbox (AggregateType, AggregateId, Payload)
        VALUES ('SalesTransaction',
                CONCAT(@TerminalID, '-', FORMAT(@BusinessDate,'yyyyMMdd'), '-', @TransactionNo),
                @Payload);
    COMMIT TRANSACTION;
END;
GO

/* ---- The forwarder agent claims a batch atomically ---- */
CREATE OR ALTER PROCEDURE dbo.usp_ClaimOutboxBatch
    @BatchSize INT = 100
AS
BEGIN
    SET NOCOUNT ON;

    /* READPAST skips rows another agent has locked; UPDLOCK+ROWLOCK claims ours.
       Two forwarder instances can run safely side by side. */
    UPDATE TOP (@BatchSize) o
    SET    o.Attempts = o.Attempts + 1,
           o.NextAttemptUtc = DATEADD(SECOND, POWER(2, LEAST(o.Attempts, 10)) , SYSUTCDATETIME())
    OUTPUT inserted.OutboxID, inserted.MessageId, inserted.AggregateId, inserted.Payload
    FROM   dbo.Outbox AS o WITH (UPDLOCK, READPAST, ROWLOCK)
    WHERE  o.SentUtc IS NULL
      AND  o.NextAttemptUtc <= SYSUTCDATETIME()
    ORDER BY o.OutboxID;      -- FIFO: preserves per-store ordering
END;
GO

CREATE OR ALTER PROCEDURE dbo.usp_MarkOutboxSent @OutboxID BIGINT
AS
BEGIN
    SET NOCOUNT ON;
    UPDATE dbo.Outbox SET SentUtc = SYSUTCDATETIME(), LastError = NULL WHERE OutboxID = @OutboxID;
END;
GO

/* Housekeeping: keep the outbox small or the forwarder slows down over time */
DELETE TOP (5000) FROM dbo.Outbox
WHERE SentUtc IS NOT NULL AND SentUtc < DATEADD(DAY, -7, SYSUTCDATETIME());

Retry with exponential backoff and jitter

Retry ladder for a store forwarder
  Attempt  Delay      Cumulative   Rationale
  ───────  ────────   ──────────   ─────────────────────────────────────────────
    1      immediate    0s         transient blip
    2      2s           2s         brief packet loss
    3      4s           6s         short WAN interruption
    4      8s          14s
    5      16s         30s
    6      32s          1m         router restart
    7      64s          2m
    8      2m           4m         ISP outage
    9      4m           8m
   10      8m          16m
   11+     30m (cap)   ...         site down; keep trying indefinitely,
                                   ALERT after 30 minutes of no contact

  Always add JITTER (±20%). Without it, 500 stores that lost the WAN together
  reconnect together and hammer the gateway in lockstep - a self-inflicted DDoS.

  NEVER discard a message because retries "ran out". The store's outbox row IS
  the transaction. It waits until the link returns.
Example · forwarder retry logic with jitter and circuit breaker
// Store-side forwarder (runs as a Windows service or container at the store)
public async Task ForwardPendingAsync(CancellationToken ct)
{
    var batch = await _store.ClaimOutboxBatchAsync(batchSize: 100, ct);
    if (batch.Count == 0) return;

    foreach (var msg in batch)
    {
        var delay = TimeSpan.FromSeconds(2);
        const int maxAttempts = 6;                 // then leave it for the next cycle

        for (var attempt = 1; attempt <= maxAttempts; attempt++)
        {
            if (_circuitBreaker.IsOpen)            // gateway is down: stop hammering it
            {
                _log.LogWarning("Circuit open; deferring {AggregateId}", msg.AggregateId);
                return;
            }

            try
            {
                using var req = new HttpRequestMessage(HttpMethod.Post, "/orders/v1/ingest")
                {
                    Content = new StringContent(msg.Payload, Encoding.UTF8, "application/json")
                };
                // The idempotency key: the server uses it to detect a duplicate delivery
                req.Headers.Add("Idempotency-Key", msg.MessageId.ToString());
                req.Headers.Add("x-store-id", _storeId.ToString());

                var res = await _http.SendAsync(req, ct);

                if (res.IsSuccessStatusCode || res.StatusCode == HttpStatusCode.Conflict)
                {
                    // 409 Conflict = already ingested. That is SUCCESS for us.
                    await _store.MarkSentAsync(msg.OutboxID, ct);
                    _circuitBreaker.RecordSuccess();
                    break;
                }

                if ((int)res.StatusCode >= 400 && (int)res.StatusCode < 500
                    && res.StatusCode != HttpStatusCode.TooManyRequests)
                {
                    // A genuine bad request will never succeed on retry - park it for a human
                    await _store.MarkPoisonAsync(msg.OutboxID, await res.Content.ReadAsStringAsync(ct), ct);
                    break;
                }
            }
            catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException)
            {
                _circuitBreaker.RecordFailure();
                _log.LogWarning(ex, "Forward attempt {Attempt} failed for {Id}", attempt, msg.AggregateId);
            }

            // Exponential backoff with +/- 20% jitter
            var jitter = 1 + (Random.Shared.NextDouble() * 0.4 - 0.2);
            await Task.Delay(TimeSpan.FromMilliseconds(delay.TotalMilliseconds * jitter), ct);
            delay = TimeSpan.FromSeconds(Math.Min(delay.TotalSeconds * 2, 1800));
        }
    }
}

Idempotent processing on the cloud side

At-least-once delivery is the only guarantee you get from a network. Assume every message will arrive twice at some point, and make the second arrival a no-op. Two layers:

    StoreID        INT              NOT NULL,

    FirstSeenUtc   DATETIME2(3)     NOT NULL DEFAULT SYSUTCDATETIME(),

    CONSTRAINT UQ_IngestKey_Business UNIQUE (StoreID, AggregateId)   -- second line of defence

GO

CREATE OR ALTER PROCEDURE dbo.usp_IngestSalesTransaction
    @IdempotencyKey UNIQUEIDENTIFIER,
    @StoreID        INT,
    @Payload        NVARCHAR(MAX),
    @OrderID        INT OUTPUT,
    @WasDuplicate   BIT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    SET @WasDuplicate = 0;

    DECLARE @AggregateId VARCHAR(60) = JSON_VALUE(@Payload, '$.transactionId');

    /* Fast path: have we seen this exact delivery, or this business transaction, before? */
    SELECT @OrderID = OrderID, @WasDuplicate = 1
    FROM   dbo.IngestKey
    WHERE  IdempotencyKey = @IdempotencyKey
       OR (StoreID = @StoreID AND AggregateId = @AggregateId);

    IF @WasDuplicate = 1
        RETURN 0;                    -- caller returns 409 Conflict; the store treats it as success

    BEGIN TRY
        BEGIN TRANSACTION;

            INSERT INTO dbo.Orders (CustomerID, StoreID, OrderDate, TotalAmount, Status)
            SELECT COALESCE(TRY_CAST(JSON_VALUE(@Payload,'$.customer.id') AS INT), 0),
                   @StoreID,
                   TRY_CAST(JSON_VALUE(@Payload,'$.capturedUtc') AS DATETIME2(3)),
                   TRY_CAST(JSON_VALUE(@Payload,'$.totals.gross') AS DECIMAL(12,2)),
                   'New';

            SET @OrderID = SCOPE_IDENTITY();

            INSERT INTO dbo.OrderLine (OrderID, ProductID, Quantity, LineAmount)
            SELECT @OrderID, p.ProductID, l.Qty, l.Qty * l.UnitPrice - l.Discount
            FROM   OPENJSON(@Payload, '$.lines')
                   WITH ( Sku VARCHAR(30) '$.sku', Qty INT '$.qty',
                          UnitPrice DECIMAL(10,2) '$.unitPrice', Discount DECIMAL(10,2) '$.discount' ) AS l
            JOIN   dbo.Product AS p ON p.ProductName = l.Sku;

            /* Recording the key is part of the SAME transaction. If this insert
               fails on the unique constraint, a concurrent duplicate won the race
               and the whole thing rolls back - exactly what we want. */
            INSERT INTO dbo.IngestKey (IdempotencyKey, StoreID, AggregateId, OrderID)
            VALUES (@IdempotencyKey, @StoreID, @AggregateId, @OrderID);

        COMMIT TRANSACTION;
        RETURN 0;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;

        IF ERROR_NUMBER() IN (2601, 2627)          -- unique violation = concurrent duplicate
        BEGIN
            SELECT @OrderID = OrderID FROM dbo.IngestKey
            WHERE  StoreID = @StoreID AND AggregateId = @AggregateId;
            SET @WasDuplicate = 1;
            RETURN 0;
        END

        THROW;
    END CATCH
END;
GO

        COALESCE(
            TRY_CAST(JSON_VALUE(s.Payload, '$.OrderTotalAmount')  AS DECIMAL(12,2)),  -- v1 name
            TRY_CAST(JSON_VALUE(s.Payload, '$.TotalAmountInclTax') AS DECIMAL(12,2))  -- v2 name
        ) AS TotalAmount,
        COALESCE(JSON_VALUE(s.Payload, '$.CustomerAccount'), 'UNKNOWN') AS CustomerAccount
FROM    dbo.D365Staging AS s
WHERE   s.ProcessedUtc IS NULL;

Reconciling a POS-to-D365 mismatch

"Store 12 says it sold 4,182 items yesterday; D365 shows 4,157." This is the most common support ticket in a hybrid retail estate. Work it in this order — it isolates the problem in minutes instead of days.

Reconciliation decision tree
  Counts disagree for Store 12, business date 2026-03-10
        │
        ├─▶ 1. Is the store's OUTBOX empty for that date?
        │      NO  → messages never left the store. Check WAN, forwarder service,
        │            circuit breaker state, and the outbox LastError column. DONE.
        │      YES ↓
        │
        ├─▶ 2. Did the cloud RECEIVE them? (count dbo.IngestKey for that store/date)
        │      NO  → lost between store and gateway: check APIM 4xx/5xx for that
        │            store's subscription, and Application Insights failures. DONE.
        │      YES ↓
        │
        ├─▶ 3. Are any messages in the DEAD-LETTER QUEUE?
        │      YES → read the DLQ reason (schema? bad SKU? unknown store?). Fix and
        │            replay. This is where "silently missing" transactions usually live.
        │      NO  ↓
        │
        ├─▶ 4. Did they reach D365? (compare SyncLog / D365 order numbers)
        │      NO  → the D365 write path failed: check Dual Write errors, OData
        │            throttling (429), or a failed batch job. DONE.
        │      YES ↓
        │
        └─▶ 5. Both sides have the rows but the NUMBERS differ:
                 • Time-zone boundary - is "business date" defined the same on both sides?
                 • Voids/returns counted differently
                 • Rounding or tax treatment
                 • Late arrivals: a store offline until 02:00 posts yesterday's sales today
               → Compare row-by-row on the natural key, not on totals.
Example · the reconciliation queries
/* A. Totals comparison, cloud vs D365, by store and business date */
WITH Cloud AS
(
    SELECT StoreID,
           CAST(OrderDate AS DATE) AS BusinessDate,
           COUNT(*)                AS OrderCount,
           SUM(TotalAmount)        AS Revenue
    FROM   dbo.Orders
    WHERE  OrderDate >= DATEADD(DAY, -3, SYSUTCDATETIME())
    GROUP BY StoreID, CAST(OrderDate AS DATE)
),
D365 AS
(
    SELECT StoreID, BusinessDate, COUNT(*) AS OrderCount, SUM(TotalAmount) AS Revenue
    FROM   dbo.D365SalesOrderStaging
    WHERE  BusinessDate >= CAST(DATEADD(DAY, -3, SYSUTCDATETIME()) AS DATE)
    GROUP BY StoreID, BusinessDate
)
SELECT  COALESCE(c.StoreID, d.StoreID)           AS StoreID,
        COALESCE(c.BusinessDate, d.BusinessDate) AS BusinessDate,
        c.OrderCount AS CloudOrders, d.OrderCount AS D365Orders,
        ISNULL(c.OrderCount,0) - ISNULL(d.OrderCount,0) AS CountDiff,
        c.Revenue    AS CloudRevenue, d.Revenue AS D365Revenue,
        ISNULL(c.Revenue,0) - ISNULL(d.Revenue,0)       AS RevenueDiff,
        CASE WHEN c.StoreID IS NULL THEN 'In D365 only - cloud never got it'
             WHEN d.StoreID IS NULL THEN 'In cloud only - D365 write path failed'
             WHEN c.OrderCount <> d.OrderCount THEN 'Count mismatch - go row by row'
             WHEN ABS(c.Revenue - d.Revenue) > 0.01 THEN 'Value mismatch - check tax/rounding/voids'
             ELSE 'Reconciled' END AS Diagnosis
FROM    Cloud AS c
FULL JOIN D365 AS d ON d.StoreID = c.StoreID AND d.BusinessDate = c.BusinessDate
WHERE   ISNULL(c.OrderCount,0) <> ISNULL(d.OrderCount,0)
   OR   ABS(ISNULL(c.Revenue,0) - ISNULL(d.Revenue,0)) > 0.01
ORDER BY BusinessDate DESC, StoreID;

/* B. Row-by-row: exactly which transactions are missing where */
SELECT  k.AggregateId,
        CASE WHEN o.OrderID IS NULL THEN 'Ingested but no order row'
             WHEN d.SalesOrderNumber IS NULL THEN 'In cloud, missing in D365'
             ELSE 'Present in both' END AS Status,
        k.FirstSeenUtc, o.OrderDate, o.TotalAmount
FROM    dbo.IngestKey AS k
LEFT JOIN dbo.Orders AS o ON o.OrderID = k.OrderID
LEFT JOIN dbo.D365SalesOrderStaging AS d ON d.SourceTransactionId = k.AggregateId
WHERE   k.StoreID = 12
  AND   k.FirstSeenUtc >= '20260310' AND k.FirstSeenUtc < '20260311'
  AND   (o.OrderID IS NULL OR d.SalesOrderNumber IS NULL);

/* C. Sync lag per store: who is silently offline right now? */
SELECT  s.StoreID,
        MAX(k.FirstSeenUtc) AS LastMessageUtc,
        DATEDIFF(MINUTE, MAX(k.FirstSeenUtc), SYSUTCDATETIME()) AS MinutesSinceLastMessage,
        CASE WHEN DATEDIFF(MINUTE, MAX(k.FirstSeenUtc), SYSUTCDATETIME()) > 120 THEN 'ALERT - store silent'
             WHEN DATEDIFF(MINUTE, MAX(k.FirstSeenUtc), SYSUTCDATETIME()) > 30  THEN 'WARN'
             ELSE 'OK' END AS Health
FROM    dbo.Store AS s
LEFT JOIN dbo.IngestKey AS k ON k.StoreID = s.StoreID
WHERE   s.IsActive = 1
GROUP BY s.StoreID
ORDER BY MinutesSinceLastMessage DESC;
/* A store that is trading but silent is the single most valuable alert in this
   architecture - it catches the failure BEFORE the day-end mismatch. */

Common mistakes and pitfalls

  • Assuming connectivity. A design that requires the WAN to be up when a sale completes will lose transactions. The till must commit locally, always.
  • At-least-once delivery without idempotency — the classic duplicate-orders incident, usually discovered in the finance reconciliation weeks later.
  • Retry without jitter, so every store reconnects simultaneously and takes down your own gateway.
  • Giving up after N retries and discarding the message. That is data loss dressed as error handling. Park it, alert, never drop.
  • A dead-letter queue nobody monitors. Alert on DLQ depth > 0.
  • Local time in payloads. Use UTC everywhere and carry both business time and arrival time.
  • Ordinal-based mapping from D365 exports, which breaks the first time a column is added.
  • Writing directly to D365 tables instead of through supported APIs — unsupported, and it breaks on upgrade.
  • Reconciling only on totals. Totals can match by coincidence while individual rows are wrong. Reconcile on the natural key.
  • No "store is silent" alert. You then discover the outage at day-end instead of within the hour.
  • Unbounded outbox growth at the store, gradually starving a small SQL Express instance.

Practical exercises and case work

  1. Architecture design workshop (60 min, in groups) Given: 180 stores, 6 lanes each, ~2,000 transactions per store per day, WAN availability 97%, finance needs day-end totals by 06:00, D365 is the system of record. Produce a labelled architecture diagram, name the technology at each hop, and write one sentence per arrow stating what happens when that hop is unavailable. Groups present and defend for 5 minutes each.
  2. Build the outbox and forwarder (50 min) Implement dbo.Outbox, usp_CompleteSale and usp_ClaimOutboxBatch in the lab database. Simulate an outage by pointing the forwarder at an unreachable endpoint for five minutes, then restore it. Verify: zero data loss, FIFO order preserved, and the backoff ladder visible in Attempts/NextAttemptUtc.
  3. Duplicate-delivery drill (40 min) Send the same payload three times with the same Idempotency-Key, and three times with different keys but the same business transaction id. Exactly one order row must exist after all six calls. Then run two ingest calls concurrently and confirm the unique-constraint race is handled without an error escaping to the caller.
  4. Reconciliation clinic (45 min) The instructor seeds four defects: a store whose forwarder is stopped, three messages in the DLQ with a bad SKU, a time-zone boundary error, and a set of late arrivals. Using only the decision tree and the reconciliation queries, learners must classify each of the four and state the fix. Twenty-minute time box, then walk through as a group.

Key takeaways

  • The store's local database is the source of truth while offline; the outbox row and the sale commit in one transaction.
  • Every hop is asynchronous, retryable and idempotent — assume at-least-once delivery everywhere.
  • Exponential backoff with jitter, a circuit breaker, and an unbounded wait: never discard a message.
  • Defend against duplicates twice: transport-level message id, and a permanent unique constraint on the business key.
  • Stage D365 data before mapping it, map by name, tolerate new fields, and monitor for drift on a schedule.
  • Reconcile on natural keys, not totals; and alert on a silent store long before day-end.

Challenge questions for the defence — instructor's list

  1. Point at any one index: which query needs it, and what happens to writes if I drop it?
  2. Show me a predicate in your code. Is it SARGable? Prove it from the plan.
  3. Your ingest endpoint receives the same order twice. Walk me through what happens.
  4. Someone deletes a day of orders at 14:37. What is your recovery sequence, and how much data do you lose?
  5. The API's P95 jumps to four seconds. Show me, in order, the four things you check.
  6. D365 renames a field in your payload next month. What breaks, and how quickly do you find out?
  7. Your Function scales to 200 instances. What fails first?
  8. What did you deliberately NOT do, and why was that the right call for this scope?

Common mistakes and pitfalls

  • Scope creep in hour one. Teams that design six endpoints deliver none. Two endpoints, complete and instrumented, is the winning shape.
  • Building the Azure tier first. Deployment and auth problems will eat the whole session. Get the database and procedures working locally, then deploy.
  • Indexes with no stated purpose. "It seemed useful" scores zero on the performance criterion. Every index needs a named query.
  • Claiming an improvement without a measurement. Capture reads and duration before you change anything — you cannot go back and get the "before" number afterwards.
  • A non-idempotent ingest endpoint. It is the single most-asked defence question, and the easiest mark to lose.
  • Passwords in local.settings.json committed to the repo. Instant deduction on the API-quality criterion, and a real habit worth breaking here.
  • Backup plan written as prose without numbers. "Regular backups" is not a plan; "full weekly, differential daily, log every 15 minutes, RPO 15 min, RTO 1 h" is.
  • Leaving documentation to the last ten minutes. Write the decision log as you make each decision — it takes two minutes then and twenty minutes later.
  • Nobody rehearses the demo. Run the end-to-end request once before you present. A failing live demo costs more time than it saves.
  • Leaving the Azure resources running. Delete the resource group after assessment, or budget for it deliberately.

Scoped project options

  1. Store order intake (default) Ingest POS order payloads, store them relationally, expose retrieval as JSON, archive orders older than 12 months. Uses every module directly. Recommended for most cohorts.
  2. Product catalogue and pricing API Read-heavy: an indexed view or columnstore for the pricing rollup, aggressive APIM response caching, and a scheduled refresh job. Good for teams stronger on reporting than transactions.
  3. Inventory movements and reconciliation Higher write volume, a partitioned movements table with monthly SWITCH archiving, and a daily reconciliation report with a "silent store" alert. The most demanding option; offer it to advanced groups.
  4. Individual fallback (self-paced learners) Same brief, but the Azure tier may be simulated: a local Functions host plus a written APIM policy and KQL queries submitted as artefacts rather than deployed. Marked on the same rubric, with the monitoring criterion assessed on the artefacts.

Key takeaways

  • A small system that is correct, measured and documented scores far higher than a large one that half works.
  • Every index, every hint and every retry setting needs a one-sentence justification you can defend.
  • Evidence beats assertion: plans, reads, durations and KQL output, not "it felt faster".
  • Document what you chose not to build — naming your limitations is a senior-engineer signal.
  • The defence is part of the assessment: being able to explain a design is what makes you the person who gets to make the next one.

Immediately — first 30 days
